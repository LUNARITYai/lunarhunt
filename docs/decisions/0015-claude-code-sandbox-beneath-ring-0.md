# ADR-0015: The Claude Code OS sandbox as a floor beneath ring 0

## Context and Problem Statement

Ring 0 (ADR-0004) decides about agent shell commands by **parsing** them. `worktree-guard`'s read-only allowlist (#49, PR #59) needed nine review rounds, and every round found another gap between our tokenizer and bash or zsh: anchoring, `&`, glued redirects, expansion, option abbreviations, continuations, comments, parentheses, zsh `&!`. #63 found more on the deny side: subshells, groups and process substitution (denied since #71). An allowlist built on a parser is in an open-ended arms race with shell syntax.

Claude Code ships an OS-level sandbox (Seatbelt on macOS, bubblewrap on Linux) for Bash commands and their child processes. It enforces filesystem and network limits in the kernel, however the command is spelled. Spike #66 tested it in a throwaway repo with real sessions on 2026-11-06 (Claude Code 2.1.319, macOS 27.0.1). The results below cite its probes (P01–P24):

- **Writes outside the task worktree are denied:**
  - into the primary checkout (P02), another worktree (P03), `~` (P04) and `/tmp` (P05);
  - through a subshell redirect into the primary (P08);
  - the writes made by `core.fsmonitor` code (P13).
- **Protected files:** the shared `.git/config` (P12), `.git/hooks` (P14) and `.claude/settings.local.json` (P15) are write-protected.
- **Secret reads:** `filesystem.denyRead` blocks shell reads of `.env` (P16). Other reads stay open by default (P17).
- **Network:** only allowlisted hosts are reachable (P18, P19). There is no egress around the proxy (P20).
- **Hooks run outside the sandbox,** so ring 0 keeps working unchanged.
- **Not covered:**
  - writes to the shared `.git` (objects, refs) from a linked worktree, so local `refs/heads/main` could be moved (P10, P11);
  - the intent of operations against an allowlisted host (`gh pr view` and `gh pr merge` both reach github.com);
  - the Read, Edit and Write tools, WebFetch, WebSearch and MCP, which all run outside the sandbox.

Cursor's sandbox (Seatbelt) was tested in a rerun (the #66 addendum). Its write boundary matches Claude Code's, except that `/tmp` is writable, and git works in worktrees, contrary to forum reports. It has no per-path read deny, though: the primary's `.env` was readable from a worktree. The Dev Container remains the phase-2 Cell (ADR-0012).

## Decision Drivers

- Enforce the shell write boundary by mechanism, not by shell parsing (constitution: rules that must hold are enforced by code).
- Keep The Charter as the single source of policy (ADR-0003): `wardens sync` generates the sandbox settings like every other tool config.
- Fail closed: no silent fallback to an unsandboxed shell, and no loss of today's approval prompts.
- Do not weaken ring 0: policy rules stay where they are.
- Keep the shell parser only where a deny-on-detection rule is cheap (#63), not as an allowlist.

## Considered Options

1. **Claude Code sandbox as a floor beneath ring 0**, generated by `wardens sync`, proven in each session, and checked by `doctor`.
2. **Ring 0 parser only**: keep hardening the tokenizer, as with #59 and #63.
3. **Dev Container per task now**, with a read-only primary mount (ADR-0012 phase 2, brought forward).
4. **Cursor sandbox as well as Claude Code's**, now.

## Decision Outcome

Chosen option: **1, the Claude Code sandbox as a floor beneath ring 0**, because it closes the whole class of differently spelled shell writes with a mechanism we do not have to maintain, and it can be generated from The Charter today.

The sandbox is **not a fifth ring and not a Warden**. It enforces no policy rule of its own. It is the OS boundary that ring 0 rules can rely on for Bash, and ADR-0004's ring table is unchanged.

The decision:

- `wardens sync` writes a `sandbox` block into the generated `.claude/settings.json`:
  - **fail-closed keys:** `enabled`, `failIfUnavailable`, `allowUnsandboxedCommands: false`, `autoAllowBashIfSandboxed: false` (approval prompts stay as they are today), and no `excludedCommands` or Unix sockets;
  - **writes:** the cwd worktree, plus sandbox-only toolchain caches under `~/.cache/panopticon-sandbox/` (the only `extra_write` location The Charter accepts);
  - **write-protected:** the worktree's Charter, its `.panopticon/`, `.claude/` and git pointer, the launcher anchor directory and the canary state directory;
  - **reads:** `denyRead` for the Charter's secret paths at any depth under the primary checkout (sibling task worktrees included) and for credential locations in the home directory;
  - **network:** an allowlist owned by The Charter, with no Anthropic API hosts.
- **The hook launcher keeps the shipped trust anchor.** It runs only the bundle of a primary listed in `~/.config/panopticon/primaries`, a file written by a human step, and never consults git (GHSA-6phq-wv5j-xq2f). Hook runs take their policy from that anchored primary (#74). No agent-writable input decides which bundle runs, because hooks run outside the sandbox with the user's privileges. This ADR adds no second anchor and no bundle hash: the sandbox closes what the sync spec left to it, shell writes to the anchor and to the primary's bundle.
- **A canary pass is bound to the effective sandbox settings.** The issued canary command is let through by an explicit hook `allow`, because it is not in `permissions.allow` and `autoAllowBashIfSandboxed` is false.
- **Sandboxed toolchains get non-secret task config** from `.panopticon/task.env`, exported into the session environment, because the worktree's `.env` stays unreadable to the shell. How `gh` and git authenticate inside the sandbox is an open decision in the spec (Decision 8).
- **An OVERSEER profile,** a separate generated settings file passed at launch, also denies writes to the repository working tree.
- **A ring-0 rule, `sandbox-guard`:**
  - it denies `dangerouslyDisableSandbox`;
  - it allows no other Bash command until an in-session **canary** has proven the sandbox boundary that fits the session's cwd.
- **`doctor`** checks that the generated settings carry the sandbox block, and that no user or local settings switch it off or widen it. It also checks that local protected branches have not moved away from `origin`.
- **Ring 0 keeps every policy rule:**
  - `scope-guard`, `protected-paths`, `secret-read-guard` and `generated-files-guard`, because the Edit, Write and Read tools run outside the sandbox;
  - `command-guard`, for network intent;
  - `worktree-guard`, whose network-side role #64 narrows;
  - the DoD.
- **The parser** stays for deny-on-detection rules (#63). Allowlists built on parsing (`primary_read_only_commands`) shrink towards #64's fixed operations.
- **Cursor stays ring-0-only** until its sandbox passes the same probes in worktrees. The Dev Container stays phase 2.

Retests R1, R6 and R7 in the spec (`docs/specs/2026-11-06-wardens-sandbox.md`) can change this design: settings precedence and path syntax, OVERSEER profile mechanics and pointer protection, and the `PostToolUse` Bash payload. This ADR is accepted only after them.

### Consequences

- Good, because writes by **Bash tool commands** outside the worktree fail in the kernel, whatever the spelling. Tested for direct writes, a subshell redirect and git-invoked code. Other forms (`eval`, interpreter one-liners) are covered by construction, since the kernel sees the same syscalls.
- Good, because shell reads of secrets and of the home directory's credential locations fail in the kernel. That removes the read half of #63's risk for Claude Code.
- Good, because Bash network egress gets an allowlist for the first time. **Only for Bash:** the allowlisted hosts themselves (github.com with the user's token), WebFetch, WebSearch and MCP remain exfiltration paths. The spec lists them as known gaps.
- Good, because `primary_read_only_commands` no longer has to be the only barrier against local writes.
- Bad, because the shared `.git` stays writable from a linked worktree. A locally moved `main` never reaches origin (ruleset, ring 3), and only `doctor protected-refs` detects it locally, unless the R3 `denyWrite` retest succeeds.
- Bad, because the sandbox is per project, not per role. The OVERSEER profile depends on how OVERSEER is launched. The canary detects a missing profile, but `doctor` cannot see a running session.
- Bad, because the generated settings live in the project and can be loosened by user or local settings unless the precedence retest shows otherwise. Without managed settings in a one-person project, this is the kind of local-config bypass ADR-0004 already accepts for ring 0.
- Bad, because hooks run outside the sandbox. The `definition-of-done` hook runs `pnpm check`, and so executes agent-written worktree code unsandboxed, unless the spec's Task 4c moves it under the sandbox profile (Decision 7).
- Bad, because every session pays a denied Bash call and a canary call, and so may each subagent. Under a hard gate this works in `-p`, headless and subagent runs only if a hook `allow` skips the prompt there (spec R4). Otherwise those runs lose Bash. The spec's Decision 2 weighs a soft gate and a hook-run canary as alternatives.
- Bad, because the minimum credential deny removes the default `gh` and git HTTPS credentials from Bash. The spec's Decision 8 chooses a narrower token, an exemption, or no pushes and PRs from inside the sandbox.
- Bad, because sandboxed toolchains need explicit cache, network and task-config entries. That is a new source of "works outside, fails inside" errors.
- Neutral: Cursor sessions get no OS floor yet; for them ring 0 alone applies, as today.

### Confirmation

- The render tests pin the generated `sandbox` block:
  - `failIfUnavailable`, `allowUnsandboxedCommands: false` and `autoAllowBashIfSandboxed: false`;
  - no `excludedCommands`;
  - the `denyWrite` and `denyRead` sets;
  - the shipped hook launcher, unchanged.
- `sandbox-guard` has DENIED/ALLOWED tables, including forged canary forms (alias, PATH shadowing, echoed output, stale nonce, resumed session) and parallel canaries with their own fixtures.
- `doctor` fails on a missing or weakened sandbox block in the generated, local or user settings, and on a moved local protected branch.
- The spike #66 probe kit, extended by the spec's retests, is kept as the manual regression suite. It is re-run after Claude Code upgrades that touch the sandbox.

## Pros and Cons of the Options

### 1. Claude Code sandbox beneath ring 0

- Good, because it enforces in the kernel, ships with the tool and is generated from The Charter.
- Good, because ring 0 is unaffected (hooks run outside the sandbox).
- Bad, because of the `.git` carve-out, the per-project scope, local-config precedence and the tools that run outside the sandbox (above).

### 2. Ring 0 parser only

- Good, because it covers Claude Code and Cursor the same way, with no new mechanism.
- Bad, because the attack surface is unbounded. #59 and #63 show the cost: many review rounds and new gaps each time.

### 3. Dev Container per task now

- Good, because it is the strongest boundary: the primary checkout is mounted read-only and the agent cannot alter its own sandbox configuration.
- Bad, because it is not tested, it is heavier per task on macOS, and ADR-0012 already places it in phase 2. It stays the target and does not replace option 1 before then.

### 4. Cursor sandbox now

- Good, because it would give both tools the same floor.
- Bad, because it has no per-path read deny, so secrets stay readable. It is also unverified whether a project can force the sandbox on, and headless `-p` reportedly ignores `sandbox.json` on Linux. Later it can serve as defence in depth for writes, through a generated `.cursor/sandbox.json`.
