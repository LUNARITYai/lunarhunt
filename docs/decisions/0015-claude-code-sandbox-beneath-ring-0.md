# ADR-0015: The Claude Code OS sandbox as a floor beneath ring 0

## Context and Problem Statement

Ring 0 (ADR-0004) decides about agent shell commands by **parsing** them. `worktree-guard`'s read-only allowlist (#49, PR #59) needed nine review rounds, and every round found another gap between our tokenizer and bash or zsh: anchoring, `&`, glued redirects, expansion, option abbreviations, continuations, comments, parentheses, zsh `&!`. #63 found more on the deny side: subshells, groups and process substitution. An allowlist built on a parser is in an open-ended arms race with shell syntax.

Claude Code ships an OS-level sandbox (Seatbelt on macOS, bubblewrap on Linux) for Bash commands and their child processes. It enforces filesystem and network limits in the kernel, however the command is spelled. Spike #66 tested it in a throwaway repo with real sessions on 2026-11-06 (Claude Code 2.1.319, macOS 27.0.1):

- **Denied:** shell writes outside the task worktree. That includes the primary checkout, another worktree, `~`, `/tmp`, a subshell redirect into the primary, and the writes made by `core.fsmonitor` code.
- **Write-protected:** `.git/config`, `.git/hooks` and `.claude/settings*.json`.
- **Read denied:** `filesystem.denyRead` blocks shell reads of `.env`.
- **Network:** only allowlisted hosts are reachable. There is no egress around the proxy.
- **Outside the sandbox:** hooks, so ring 0 keeps working unchanged.
- **Not covered:** writes to the shared `.git` (objects, refs) stay allowed from a linked worktree, so a worktree session could move local `refs/heads/main`. The sandbox also cannot distinguish operations against an allowlisted host (`gh pr view` and `gh pr merge` both reach github.com).

Cursor's sandbox could not be tested: headless trust blocked the run. Forum reports say it breaks git in worktrees. The Dev Container remains the phase-2 Cell (ADR-0012).

## Decision Drivers

- Enforce the write boundary by mechanism, not by shell parsing (constitution: rules that must hold are enforced by code).
- Keep The Charter as the single source of policy (ADR-0003): `wardens sync` generates the sandbox settings like every other tool config.
- Fail closed: no silent fallback to an unsandboxed shell.
- Do not weaken ring 0: policy rules stay where they are.
- Keep the shell parser only where a deny-on-detection rule is cheap (#63), not as an allowlist.

## Considered Options

1. **Claude Code sandbox as a floor beneath ring 0**, generated by `wardens sync` and checked by `doctor`.
2. **Ring 0 parser only**: keep hardening the tokenizer, as with #59 and #63.
3. **Dev Container per task now**, with a read-only primary mount (ADR-0012 phase 2, brought forward).
4. **Cursor sandbox as well as Claude Code's**, now.

## Decision Outcome

Chosen option: **1, the Claude Code sandbox as a floor beneath ring 0**, because it closes the whole write-spelling class with a mechanism we do not have to maintain, and it can be generated from The Charter today.

The sandbox is **not a fifth ring and not a Warden**. It enforces no rule of its own. It is the OS boundary that ring 0 rules can rely on. ADR-0004's ring table is unchanged.

The decision:

- `wardens sync` writes a `sandbox` block into the generated `.claude/settings.json`:
  - `enabled: true`, `failIfUnavailable: true`, `allowUnsandboxedCommands: false`, no `excludedCommands`;
  - writes: the cwd worktree (the default), plus the Charter `paths.external.write` and the package-manager caches the toolchain needs;
  - reads: `denyRead` from the Charter `paths.secrets_deny_read`;
  - network: an allowlist from a new Charter `sandbox.network.allow` key.
- An **OVERSEER profile** (a separate settings file passed at launch) additionally denies writes to the repository working tree. The OVERSEER cwd then becomes read-only at kernel level.
- `doctor` checks that the generated settings carry the sandbox block, and that no user or local settings switch it off or widen it.
- A ring-0 rule denies Bash calls that ask for `dangerouslyDisableSandbox`. This is defence in depth on top of `allowUnsandboxedCommands: false`.
- **Ring 0 keeps every policy rule:**
  - `scope-guard` and `protected-paths` (Edit and Write run outside the sandbox);
  - `secret-read-guard` (the Read tool runs outside the sandbox);
  - `command-guard` (network intent);
  - `worktree-guard`, whose network-side role is narrowed by #64;
  - the DoD.
- The parser stays for deny-on-detection rules (#63). Allowlists built on parsing (`primary_read_only_commands`) shrink towards #64's fixed operations.
- **Cursor stays ring-0-only** until its sandbox passes the same probes in worktrees. The Dev Container stays phase 2.

Rollout depends on the retest items listed in the spec (`docs/specs/2026-11-06-wardens-sandbox.md`): settings precedence, the full toolchain inside the sandbox, `denyWrite` on `refs/heads/main`, and the `dangerouslyDisableSandbox` refusal.

### Consequences

- Good, because shell writes outside the worktree fail in the kernel, whatever the spelling. Subshells, redirects, `eval` and interpreter one-liners are covered alike.
- Good, because shell reads of secrets fail in the kernel, which removes the read half of #63's risk for Claude Code.
- Good, because network egress gets an allowlist for the first time; exfiltration to arbitrary hosts is blocked.
- Good, because `primary_read_only_commands` no longer has to be the only barrier against local writes.
- Bad, because the shared `.git` stays writable from a linked worktree. Moving local `main` is caught only by the `main` ruleset (ring 3) and `doctor`, unless the `denyWrite` retest succeeds.
- Bad, because the sandbox is per project, not per role. The OVERSEER profile depends on Krzysztof launching OVERSEER with the right settings file. `doctor` cannot see a running session's profile.
- Bad, because the generated settings live in the project and can be loosened by user or local settings unless the precedence retest shows otherwise. Without managed settings in a one-person project, this is a local-config bypass of the kind ADR-0004 already accepts for ring 0.
- Bad, because sandboxed toolchains need explicit cache and network entries, a new source of "works outside, fails inside" errors.
- Neutral: Cursor sessions get no OS floor yet; for them ring 0 alone applies, as today.

### Confirmation

- The render tests pin the generated `sandbox` block, including `failIfUnavailable`, `allowUnsandboxedCommands: false` and the absence of `excludedCommands`.
- `doctor` fails on a missing or weakened sandbox block in the generated, local or user settings.
- An in-session canary: hooks run outside the sandbox and cannot probe it, so ring 0 requires one sandboxed Bash run of `wardens sandbox canary` per session before any other Bash command. The canary must fail to write outside the worktree, and ring 0 records the result. The spec gives the design.
- The spike #66 probe kit is kept as the manual regression suite and re-run after Claude Code upgrades that touch the sandbox.

## Pros and Cons of the Options

### 1. Claude Code sandbox beneath ring 0

- Good, because it enforces in the kernel, ships with the tool and is generated from The Charter.
- Good, because ring 0 is unaffected (hooks run outside the sandbox).
- Bad, because of the `.git` carve-out, per-project scope and local-config precedence (above).

### 2. Ring 0 parser only

- Good, because it covers Claude Code and Cursor the same way, with no new mechanism.
- Bad, because the attack surface is unbounded. #59 and #63 show the cost: many review rounds and new gaps each time.

### 3. Dev Container per task now

- Good, because it is the strongest boundary: the primary checkout is mounted read-only and the agent cannot alter its own sandbox configuration.
- Bad, because it is not tested, it is heavier per task on macOS, and ADR-0012 already places it in phase 2. It stays the target and does not replace option 1 before then.

### 4. Cursor sandbox now

- Good, because it would give both tools the same floor.
- Bad, because it is not tested (headless trust), git is reported broken in worktrees under it, and headless `-p` reportedly ignores `sandbox.json` on Linux.
