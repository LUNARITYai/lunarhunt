# ADR-0012: Task isolation with git worktrees

## Context and Problem Statement

The Covenant says "one task, one branch, one PR" (C-11), but nothing says *where* an agent does the work. A local agent started in Krzysztof's checkout edits his working tree directly: it can mix its changes with his uncommitted work, run on `main`, and two agents (or an agent and a human) cannot work in parallel without colliding. Nightly Cells (ADR-0007) were planned to "run the Dev Container per task with their own git worktree", but the worktree part was never specified.

Both agent tools now ship native worktree support. Claude Code has `claude --worktree`, subagent `isolation: worktree` and `WorktreeCreate`/`WorktreeRemove` hooks. Cursor has `agent --worktree` with `--worktree-base`, and runs `.cursor/worktrees.json` setup commands for every new worktree. The two tools use different default locations, branch names and cleanup rules. A fresh worktree also has no `node_modules`, no `.venv`, no Wardens bundle and no `.env`. Parallel worktrees then compete for the same docker compose project, ports and database.

We need one rule for where agents work, the same naming in both tools, environment setup that never copies secrets, a plan for shared resources and cleanup, and a Warden that enforces the rule.

## Decision Drivers

- Agents never touch the primary checkout or `main`; humans keep their normal workflow
- Parallel tasks (agent + agent, agent + human) without file, port or database collisions
- Use the tools' native mechanisms, configured from The Charter (ADR-0003), not hand-written per tool
- Same branch and worktree naming in both tools, so The Ledger links every run to its issue
- Fresh worktree is ready for `pnpm check` without manual steps; no secrets copied
- Cheap enough for interactive local work in phases 0–1; a base for nightly Cells in phase 2
- Deterministic enforcement in ring 0, backed by later rings (C-01, C-02)

## Considered Options

1. **Git worktree per task** (one task = one branch = one worktree), created through the tools' native mechanisms and a shared `wardens worktree` setup
2. **Separate clone per task**
3. **Work in the primary checkout** on a task branch (status quo)
4. **Container-only isolation**: every task in its own Dev Container with its own clone or volume

## Decision Outcome

Chosen option: **git worktree per task (1)**, because it isolates files and branches at almost no cost (one shared `.git` object store, seconds to create), is supported natively by both Claude Code and Cursor, and composes with the Dev Container: in phases 0–1 the worktree *is* the lightweight local Cell, and nightly Cells later run the Dev Container on top of a worktree.

### Rules

- **One task = one issue = one branch = one worktree = one PR.** The worktree lives until the PR is merged or closed.
- **Agents never edit files in the primary checkout** (the main working tree of the repository) **and never on `main`**, in any tool, any role and any autonomy phase. Read-only work (reading files, `git status`, `git log`, `rg`) in the primary checkout stays allowed, so OVERSEER can plan from there.
- **Humans may still work in the primary checkout**; `worktree-guard` runs only in ring 0 (agent hooks). The `main` ruleset (ring 3) still prevents anyone from pushing to `main` directly.
- **Read-only roles** (`reviewer`, `sentinel`, `debugger`) need no worktree of their own; they read the task's worktree or the PR diff.

### Naming

- **Worktree name:** `<issue-number>-<slug>`, e.g. `42-offer-crud`. The slug is lowercase kebab-case, at most 40 characters.
- **Branch:** `<type>/<issue-number>-<slug>`, e.g. `feat/42-offer-crud`, unchanged from C-09 and ADR-0001. `<type>` comes from the issue's `type:*` label. The worktree name is always the branch name without the type prefix (decided 2026-11-04; C-09 unchanged), so the issue number is recoverable from both.
- **Sub-worktrees** (parallel implementer subagents inside one task, see below) are named `<issue-number>-<slug>--<suffix>` on branch `<type>/<issue-number>-<slug>--<suffix>`. They are merged back into the task branch by the parent session and never get their own PR.
- **The Ledger** records `issue`, `branch`, `worktree` (name and path) and `primary_checkout` (boolean, must be false for agent edits) on every `run`. This extends the `run` table of ADR-0010 without changing its other fields.

### One creation path, three entry points

All three entry points end in the same engine code, `wardens worktree create`, so naming, base ref, setup and resource allocation are identical:

| Entry point | Mechanism (generated by `wardens sync`) | Location |
|-------------|------------------------------------------|----------|
| Human or OVERSEER from a shell | `wardens worktree new <issue> [--slug <slug>]` runs `git fetch origin main` and `git worktree add -b <type>/<issue>-<slug> .claude/worktrees/<issue>-<slug> origin/main`, then runs setup | `<repo>/.claude/worktrees/<name>` |
| Claude Code (`claude --worktree <name>`, `claude --bg --worktree <name>`, `claude -p --worktree <name>`, subagents with `isolation: worktree`) | A **`WorktreeCreate` hook** in `.claude/settings.json` calling `node "${CLAUDE_PROJECT_DIR}/wardens/dist/wardens.mjs" worktree create --tool claude`. It reads `name` from the hook input, creates the worktree as above and prints its path. A **`WorktreeRemove` hook** calls `wardens worktree remove`. | `<repo>/.claude/worktrees/<name>` (Claude Code's default location, kept so `--resume` and `EnterWorktree` work without extra prompts) |
| Cursor CLI and Agents Window (`agent -w <name> --worktree-base origin/main`) | Cursor creates the worktree; **`.cursor/worktrees.json`** runs `setup-worktree-unix: ["node \"$ROOT_WORKTREE_PATH/wardens/dist/wardens.mjs\" worktree setup --tool cursor"]`. Setup always switches the worktree to the convention branch (`git switch -c <type>/<issue>-<slug>`), whatever branch name Cursor created, so Cursor's own naming does not matter. | `~/.cursor/worktrees/<repo>/<name>` (fixed by Cursor) |

Claude Code subagents: `wardens sync` writes `isolation: worktree` into the frontmatter of the `implementer` subagent definition (`.claude/agents/implementer.md`). Read-only roles do not get it. Because the `WorktreeCreate` hook replaces Claude Code's git logic, a subagent worktree gets our naming: a name that does not match `<issue>-<slug>` is treated as a sub-worktree of the task branch checked out in the hook's `cwd`, based on that branch's `HEAD`. If the hook's `cwd` is the primary checkout on `main`, the hook fails with a Warden-format message.

OVERSEER background sessions (phase 1): `claude --bg --worktree <issue>-<slug> "<prompt>"` or `agent -p -w <issue>-<slug> --worktree-base origin/main "<prompt>"`.

Base ref: always `origin/main` after a fetch. In Claude Code the hook decides the base, which matches its default `worktree.baseRef: "fresh"`. In Cursor, `--worktree-base origin/main` is passed explicitly, because Cursor's default is the current `HEAD`.

### Worktree setup (`wardens worktree setup`)

Runs in the new worktree, the same for both tools:

1. `pnpm install --frozen-lockfile` (no symlinked `node_modules`; Cursor's docs advise against symlinking dependencies).
2. `uv sync --frozen`.
3. `pnpm --filter wardens build`, so the worktree has its own `wardens/dist/wardens.mjs` for lefthook and `pnpm check`. Ring-0 hooks keep running the **primary checkout's** bundle (`${CLAUDE_PROJECT_DIR}` and `$ROOT_WORKTREE_PATH` point there), so an agent cannot weaken a guard by editing the engine inside its worktree.
4. `lefthook install` (git hooks are shared through the common `.git`, so this is idempotent).
5. **Environment file:** writes `.env` from the committed template `.env.example` (readable by agents and setup as an explicit exception to the Charter's `secrets_deny_read`, ADR-0013; it never contains real secrets and gitleaks scans it), filling in only per-task values: `TASK_ISSUE`, `DATABASE_URL` for the task database, `WEB_PORT`, `API_PORT`, `COMPOSE_PROJECT_NAME`. **Nothing is copied from the primary checkout.** There is no `.worktreeinclude` (Claude Code ignores it anyway when a `WorktreeCreate` hook is used), and `setup-worktree` never runs `cp $ROOT_WORKTREE_PATH/.env`. Local development needs no secrets; anything that does (e.g. an LLM API key) comes from the developer's shell environment or the Dev Container's environment, never from a file in the worktree.
6. Creates the task database and runs migrations (see below).
7. Emits a Ledger `worktree_created` event (issue, branch, worktree, tool).

A failing step fails the whole setup. Cursor's `--skip-worktree-setup` and any worktree without a successful setup marker are reported by `wardens doctor` and blocked by the `definition-of-done` Warden, because `pnpm check` cannot pass there.

### Shared resources: shared services, database per task

Chosen for local work (phases 0–1): **one shared services stack plus a database per task**, not a full docker compose stack per worktree.

- The Dev Container's compose project (Postgres, local Grafana stack) runs **once**, from the primary checkout, under `COMPOSE_PROJECT_NAME=lunarhunt`. Worktrees do not start their own Postgres or Grafana.
- Each task gets its own database `lunarhunt_t<issue>` (e.g. `lunarhunt_t42`) on the shared Postgres, created by setup and migrated with the task branch's migrations. The Ledger keeps its own `ledger` database, shared by all tasks.
- App processes started from a worktree (Next.js dev server, uvicorn, worker) use ports derived from the issue number: `WEB_PORT = 30000 + (issue mod 1000)`, `API_PORT = 31000 + (issue mod 1000)`. Two open issues that collide modulo 1000 are detected by setup, which fails with a clear message.
- If a task really needs its own container (e.g. testing a compose change), it runs with `COMPOSE_PROJECT_NAME=lunarhunt-t<issue>` and the same port offset. This is the exception, not the default.

Reasoning: a full stack per worktree (Postgres + Loki + Tempo + Prometheus + Grafana) costs several hundred MB of RAM and a minute of start-up per task on a laptop, for isolation local work does not need. A database per task gives the isolation that matters (schemas and migrations from different branches cannot conflict, test data does not leak between tasks). Port offsets are deterministic, so The Ledger and humans can find a task's app without asking.

**Nightly Cells (phase 2, ADR-0007)** use the opposite: a **full stack per Cell**. The Dev Container runs per task on top of the task's worktree, with its own compose project `cell-<run-id>`, its own Postgres and Charter-defined egress limits. Unattended runs need full isolation, including from each other's crashes.

### Cleanup

- `wardens worktree remove <name>` removes the worktree (`git worktree remove`), drops `lunarhunt_t<issue>`, deletes the local branch if it is merged, and records a `worktree_removed` Ledger event. It refuses when there are uncommitted changes or unpushed commits; `--force` is for humans only (the `command-guard` Warden denies it for agents).
- `wardens worktree prune` (run by a human, later by a scheduled job) removes every worktree whose PR is merged or closed (checked with `gh`), and lists the rest.
- `wardens doctor` reports: stale worktrees (no commit for `stale_after_days`, or PR merged or closed), orphan `lunarhunt_t*` databases without a worktree, worktrees without a successful setup, missing `.claude/worktrees/` exclusions in `.gitignore`, `biome.json`, `tsconfig.base.json` and Ruff/Pyright settings, and Cursor's machine-wide `cursor.worktreeMaxCount`.
- **Tool cleanup is not relied on.** Claude Code's periodic sweep skips worktrees it did not create with its own git logic, so it never removes ours. Cursor's cleanup keeps at most `cursor.worktreeMaxCount` worktrees per machine (default 25) and treats worktrees created outside its manager as eligible for deletion. Its documentation does not say whether it skips worktrees with uncommitted work, so agents push their task branch early (draft PR) and `wardens doctor` warns when the limit is close.

### Enforcement: Warden `worktree-guard`

Ring 0 (Claude Code `PreToolUse`, Cursor `preToolUse` / `beforeShellExecution`), fail-closed like every protective Warden (ADR-0005).

- **Detection** from the hook's `cwd` (Claude Code passes the real working directory in `cwd`; `${CLAUDE_PROJECT_DIR}` stays at the primary checkout):
  - primary checkout: `git rev-parse --path-format=absolute --git-dir` equals `git rev-parse --path-format=absolute --git-common-dir`;
  - linked worktree: the two differ (`.git/worktrees/<name>` vs `.git`);
  - branch: `git branch --show-current`; empty means detached `HEAD`.
- **Blocks** for agent sessions when the cwd is the primary checkout, or the branch is `main`, a protected branch or detached:
  - every `edit`, `write` and `delete` action;
  - every `shell` command not on the Charter's `worktree.primary_read_only_commands` list.
  - Edits whose target path resolves into the primary checkout from inside a worktree are blocked too (`git rev-parse --show-toplevel` of the target).
- **Allows** in the primary checkout: reads, the read-only command list, `wardens worktree new|list|doctor`, and starting a worktree session (`claude --worktree …`, `agent -w …`).
- **Messages** (C-30 format):
  - `Blocked by Warden worktree-guard: edits in the primary checkout are not allowed for agents. Run "wardens worktree new 42" and continue in .claude/worktrees/42-offer-crud.`
  - `Blocked by Warden worktree-guard: branch main is protected. Create a task worktree with "wardens worktree new <issue>".`
  - `Blocked by Warden worktree-guard: worktree 42-offer-crud is on branch fix/41-typo, expected feat/42-offer-crud. Switch back with "git switch feat/42-offer-crud".`
- **Path rules are evaluated relative to the worktree root** (`git rev-parse --show-toplevel` of the cwd), not the primary checkout. Otherwise every file in `.claude/worktrees/**` would match the protected glob `.claude/**`, and `scope-guard`, `protected-paths` and `generated-files-guard` would misfire.
- **Defense in depth (C-02):** this rule is local by nature, so CI cannot re-check it directly. Backstops: the `main` ruleset (ring 3) rejects direct pushes to `main`; `pr-check` (ring 2) enforces the branch convention; The Ledger flags agent runs with `primary_checkout: true` or without a `worktree` value. In Claude Code, a session started with `--worktree` additionally gets Claude Code's built-in isolation checks (edits and git redirects into the main checkout are refused).

### Charter extension (sketch)

This ADR extends the ADR-0003 schema (v1) with a new top-level `worktree:` section; ADR-0003 itself is not edited. The JSON Schema `wardens/schema/charter.schema.json` gains the section in the implementation PR.

```yaml
worktree:                                  # ADR-0012
  required_for_agents: true                # worktree-guard on; false only via a Charter PR
  protected_branches: ["main"]
  base_ref: "origin/main"
  naming:
    worktree: "{issue}-{slug}"             # 42-offer-crud
    branch: "{type}/{issue}-{slug}"        # feat/42-offer-crud (C-09)
    sub_suffix: "--{suffix}"               # parallel subagent worktrees
    slug_max_length: 40
  location:
    default: ".claude/worktrees/{name}"    # wardens worktree new + Claude Code
    cursor: "~/.cursor/worktrees/{repo}/{name}"   # fixed by Cursor, informational
  isolation_roles: ["implementer"]         # subagents generated with isolation: worktree
  setup:
    steps: ["pnpm install --frozen-lockfile", "uv sync --frozen",
            "pnpm --filter wardens build", "lefthook install"]
    env_template: ".env.example"           # readable exception to secrets_deny_read (ADR-0013); per-task values only
    copy_from_primary: []                  # must stay empty (schema: maxItems 0)
  resources:
    strategy: shared-services-db-per-task  # nightly Cells: per-cell-stack (ADR-0007)
    shared_compose_project: "lunarhunt"
    database: "lunarhunt_t{issue}"
    ports: { web: 30000, api: 31000, offset: "issue % 1000" }
  primary_read_only_commands: ["git status*", "git log*", "git diff*", "git fetch*",
            "git worktree list*", "rg *", "ls*", "cat *", "wardens worktree *",
            "wardens doctor*", "claude --worktree *", "claude -w *", "agent -w *",
            "agent --worktree *"]
  cleanup:
    stale_after_days: 7
    remove_on: [pr_merged, pr_closed]
    drop_database: true
```

### Generated files (by `wardens sync`)

- `.claude/settings.json`: `WorktreeCreate` and `WorktreeRemove` hooks; `worktree-guard` added to `PreToolUse`; `worktree.baseRef: "fresh"`.
- `.claude/agents/implementer.md`: `isolation: worktree` in the frontmatter.
- `.cursor/worktrees.json`: `setup-worktree-unix` (and a `setup-worktree` fallback) calling `wardens worktree setup`.
- `.cursor/hooks.json`: `worktree-guard` on `preToolUse` and `beforeShellExecution`.
- Not generated, but required and checked by `wardens doctor`: `.claude/worktrees/` is excluded in `.gitignore`, `biome.json`, `tsconfig.base.json` and `pyproject.toml` (Ruff and Pyright), so the primary checkout does not show, lint or type-check worktree files.

### Relation to Cells

| Phase | Cell | Isolation |
|-------|------|-----------|
| 0–1 | **Local Cell = task worktree** on the developer machine or inside the shared Dev Container | Files and branch (worktree), database (`lunarhunt_t<issue>`), ports (offset). No network or process isolation. |
| 2+ | **Nightly Cell** = Dev Container per task on top of the task worktree (ADR-0007) | Everything above plus own compose stack, own Postgres and Charter egress limits |

When the Dev Container is used, worktrees must be created **inside the same environment that runs the agent**. A worktree's `.git` file holds an absolute path to the common `.git`, which differs between host and container. Worktrees under `.claude/worktrees/` are inside the mounted workspace, so they work in both. Cursor's `~/.cursor/worktrees/` is outside the mount and only works when the Cursor CLI runs in the same environment as the repository.

### Consequences

- Good, because agents can no longer damage the primary checkout or `main`, and Krzysztof can keep working while agents run.
- Good, because several agents can work in parallel without file, port or database collisions.
- Good, because both tools use their native mechanisms, but naming, setup and cleanup are one engine implementation driven by The Charter.
- Good, because ring-0 hooks always run the primary checkout's Wardens bundle, which agents cannot edit.
- Good, because every Ledger run is tied to an issue, branch and worktree, and the local Cell becomes a measurable concept before nightly Cells exist.
- Bad, because each worktree costs a full `pnpm install` and `uv sync` (pnpm's content-addressed store and uv's cache keep this to seconds after the first run) and disk space for `node_modules` and `.venv`.
- Bad, because a database per task on shared Postgres gives no protection against a task that breaks the shared server (e.g. exhausts connections); accepted for local work, solved by per-Cell stacks at night.
- Bad, because the `WorktreeCreate` hook replaces Claude Code's built-in worktree logic, so we own creation, `.worktreeinclude` behaviour and cleanup for Claude Code sessions.
- Bad, because Cursor's worktree location and cleanup are fixed by Cursor; we can only configure and monitor them.
- Bad, because `worktree-guard` cannot be re-checked in CI; it relies on ring 3 and Ledger backstops.
- Neutral, because humans are not forced into worktrees; they may adopt `wardens worktree new` for parallel work.

### Confirmation

- **Wardens unit tests** (`pnpm --filter wardens test`, CI job `wardens-test`), on real temporary git repositories with a linked worktree:
  - `worktree-guard` blocks an `edit` and a non-allowlisted `shell` command in the primary checkout, on `main` and on a detached `HEAD`; allows them in a linked worktree on a convention branch; blocks an edit whose target resolves into the primary checkout from inside a worktree;
  - every block message matches `Blocked by Warden worktree-guard: … .` and names a next action;
  - contract tests on recorded Claude Code (`PreToolUse`, `WorktreeCreate`, `WorktreeRemove`) and Cursor (`preToolUse`, `beforeShellExecution`) payloads, including the `cwd` field;
  - `wardens worktree create` produces `<issue>-<slug>` / `<type>/<issue>-<slug>`, rejects invalid names, allocates `lunarhunt_t<issue>` and the expected ports, and never writes a value from the primary checkout's `.env` into the new `.env` (seeded secret test);
  - `wardens worktree remove` refuses with uncommitted or unpushed work and drops the database otherwise.
- **`charter-validate`**: the `worktree:` section validates against the JSON Schema; `copy_from_primary` must be empty. Turning `required_for_agents` off is a Charter change, so it is always `risk:high` and needs Krzysztof (C-23).
- **`charter-drift`**: `.claude/settings.json`, `.claude/agents/implementer.md`, `.cursor/worktrees.json` and `.cursor/hooks.json` match `wardens sync` output.
- **`wardens doctor`**: the `WorktreeCreate` hook and `worktree-guard` are present and fail-closed; `.cursor/worktrees.json` exists and calls `wardens worktree setup`; worktree exclusions are present; lists stale worktrees, orphan task databases and worktrees without setup; warns when Cursor's worktree count is near `cursor.worktreeMaxCount`.
- **The Ledger** flags agent runs with `primary_checkout: true`, without a `worktree` value, or whose `branch` does not contain the run's issue number.
- **`pr-check`** (existing) enforces the `<type>/<issue>-<slug>` branch convention.
- **`secret-read-guard`** tests (ADR-0013): setup may read `.env.example`; reading the primary checkout's `.env` is denied.

## Pros and Cons of the Options

### Git worktree per task

- Good, because it is fast and cheap (shared object store), and native in both Claude Code and Cursor.
- Good, because it keeps branch and files together, which maps cleanly to issue → branch → PR.
- Bad, because dependencies, `.env` and databases must be set up per worktree, and tools differ in location, naming and cleanup.

### Separate clone per task

- Good, because isolation is complete, including the git config and hooks.
- Bad, because it is slower, uses more disk, duplicates objects and needs its own remote setup; neither tool creates clones natively.

### Work in the primary checkout

- Good, because there is nothing to set up.
- Bad, because agents mix with human work, can edit on `main`, and parallel work is impossible.

### Container-only isolation

- Good, because it isolates processes, network and data as well as files.
- Bad, because it is too heavy for interactive local work (start-up time, RAM, editor integration), and it still needs a checkout per task inside the container, so it does not replace worktrees. Chosen for nightly Cells on top of worktrees.
