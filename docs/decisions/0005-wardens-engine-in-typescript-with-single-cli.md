# ADR-0005: Wardens engine in TypeScript with a single CLI

## Context and Problem Statement

The same Warden rules (ADR-0004) must run from Claude Code hooks, Cursor hooks, lefthook and CI. Claude Code and Cursor use different hook event names, payloads and tool names (Claude: `Bash`, `Edit`, `Write`, `mcp__server__tool`; Cursor: `Shell`, `Read`, `Write`, `Grep`, `Delete`, `Task`, `MCP:<tool>`). Both tools default to letting an action through when a hook crashes or times out unless configured otherwise. Cursor can also load Claude Code hooks from `.claude/settings.json`, which, combined with a native `.cursor/hooks.json`, can run the same Warden twice. We need one engine, one language and one invocation contract.

## Decision Drivers

- One implementation of each rule for all four rings
- A language the maintainer prefers for CLI tooling and will keep improving
- Typed validation of The Charter and hook payloads
- No extra toolchain beyond what the monorepo already has (Node + pnpm)
- Fast start-up (hooks run on every tool call)
- Easy, thorough testing against recorded hook payloads
- Fail-closed behaviour for security-relevant hooks
- Error messages an agent can act on without guessing

## Considered Options

1. **TypeScript** CLI `wardens` on Node, bundled into a single file, tested with Vitest
2. **Python** CLI, managed with uv, tested with pytest
3. TypeScript on Bun
4. Separate shell scripts per tool and per rule

## Decision Outcome

Chosen option: **TypeScript CLI `wardens` on Node**, because the maintainer prefers TypeScript for CLI tooling, the TS ecosystem has mature CLI and schema libraries, Node and pnpm are already part of the monorepo and the Dev Container, and Vitest makes payload-driven tests simple. Guards are internal tooling and do not need to share a language with the FastAPI backend.

The decision is cheap to reverse: Wardens are reached only through a process contract (hook JSON on stdin, exit code plus JSON on stdout, Charter as YAML). Rewriting the engine in another language does not touch The Charter, the generated tool configs' structure or CI wiring; recorded payload fixtures stay valid as the contract test suite.

### Design

- **Package:** `wardens/` in the monorepo (ADR-0007), a pnpm workspace package with its own `package.json` and `AGENTS.md`, binary `wardens`.
- **Stack:** TypeScript in strict mode, Biome (ADR-0007), **zod** schemas for The Charter and for every hook payload, a small CLI library (for example `commander` or `citty`; picked in the skeleton task), **Vitest** for tests. Runtime: Node LTS pinned in the Dev Container.
- **Build:** **tsup** bundles the CLI into one file `wardens/dist/wardens.mjs` with no runtime dependency resolution, so a hook only pays Node start-up. The bundle is built on Dev Container create and by `pnpm --filter wardens build`; it is not committed. A missing bundle makes the hook fail, which the fail-closed settings below turn into a block.
- **Single CLI, one subcommand per entry point**, for example:
  - `wardens hook --tool claude|cursor --event <event>` (ring 0; reads the hook JSON from stdin)
  - `wardens check <rule>` and `wardens pr-check` (rings 1 and 2)
  - `wardens sync` (generate tool configs from The Charter, ADR-0003), `wardens doctor` (self-test)
- **Thin tool configs** generated by `wardens sync`:
  - `.claude/settings.json`: `PreToolUse` (matcher `Bash|Edit|Write|mcp__.*`), `PostToolUse` (`Edit|Write`), `Stop`, each calling `node "${CLAUDE_PROJECT_DIR}/wardens/dist/wardens.mjs" hook --tool claude …` with `onFailure: "block"` and a timeout; plus `permissions.deny` / `ask` / `allow` generated from The Charter (hard allow/deny belongs in the permission system, hooks add context-aware rules).
  - `.cursor/hooks.json`: `preToolUse`, `beforeShellExecution`, `beforeMCPExecution`, `beforeReadFile`, `afterFileEdit`, `stop`, each with `failClosed: true`.
- **Normalization layer:** adapters convert each tool's payload into one internal event (`action: shell|read|edit|write|delete|mcp`, `path`, `command`, `mcp_server`, `session_id`, `agent`, `model`). Rules only see the normalized event, so `Bash` and `Shell` are the same rule.
- **Fail-closed:** a blocking decision is returned in the tool's native form (Claude Code: exit code 2 or a JSON `permissionDecision: deny`; exit code 1 is non-blocking and must never be used for enforcement). Any internal error in a protective hook results in *deny*. The tool-level settings (`onFailure: "block"`, `failClosed: true`) cover crashes, timeouts and wrong paths.
- **No double execution:** Cursor's import of Claude Code hooks is **disabled**; each tool has its own native config. The native Cursor config is preferred because it supports `failClosed` and `beforeShellExecution`. As a second line, the engine is idempotent and records a hook-event fingerprint in The Ledger, so a duplicate run is detected.
- **Every verdict is logged** to The Ledger (rule ID, outcome, duration), see ADR-0010.
- **Actionable error messages**, one format for all rules:

  ```text
  Blocked by Warden <rule-id>: <what was blocked and why>. <Next allowed action>.
  ```

  Example: `Blocked by Warden scope-guard: path infra/ not in allowed_paths for this task. Ask for needs:human.`

### Consequences

- Good, because a rule is written and tested once and behaves the same in every ring and both tools.
- Good, because the normalization layer isolates us from frequent changes in hook APIs.
- Good, because agents get a precise next step instead of a bare refusal.
- Good, because the engine is written in the maintainer's preferred language for CLI tools and shares tooling (Biome, pnpm, Turborepo) with the web app.
- Bad, because every tool call pays Node start-up time (bundling avoids TS compilation and module resolution at run time); hooks need a strict timeout and must stay lean.
- Neutral, because Python remains a valid fallback; switching costs a rewrite of the engine only, guarded by the same payload fixtures.
- Bad, because disabling Cursor's Claude hook import is an editor setting, not a repo file, so it is checked rather than guaranteed.
- Bad, because hook payload formats change often; contract tests with recorded payloads must be updated with each tool upgrade.

### Confirmation

- CI job `wardens-test`: `pnpm --filter wardens test` (Vitest) including contract tests on recorded Claude Code and Cursor payloads for every hook event used.
- `wardens doctor` (in `wardens-test` and runnable locally) checks that generated configs contain `onFailure: "block"` / `failClosed: true` for every protective hook, breaks a hook on purpose and asserts the action is blocked, and warns when the same hook event is observed twice in one session (Cursor import still enabled).
- CI job `charter-drift` (ADR-0003) fails if `.claude/settings.json` or `.cursor/hooks.json` were edited by hand.
- A unit test asserts every block message matches the format `Blocked by Warden <rule-id>: … .`.

## Pros and Cons of the Options

### TypeScript on Node + tsup + Vitest

- Good, because it is the maintainer's preferred language for CLI tooling and has mature CLI and schema libraries (zod).
- Good, because it is closer to the hook examples in Cursor's and Claude Code's documentation and reuses the monorepo's Node toolchain.
- Bad, because of Node start-up cost on every hook (mitigated by a single-file bundle).

### Python + uv + pytest

- Good, because it is one language with the backend and easy to test.
- Bad, because the maintainer prefers TypeScript for CLI tooling, and interpreter plus uv start-up cost is paid on every hook.

### TypeScript on Bun

- Good, because of fast start-up and built-in TS execution.
- Bad, because it adds a second JS runtime next to Node used by Next.js and tooling; can be revisited if Node start-up becomes a measured problem.

### Shell scripts

- Good, because there are no dependencies.
- Bad, because they are hard to test, duplicated per tool and fragile in parsing JSON.
