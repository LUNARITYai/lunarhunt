# Ledger v0: run events in JSONL and a phase-1 criteria report

## Goal and context

Issue [#98](https://github.com/LUNARITYai/lunarhunt/issues/98) makes the ADR-0008 phase-1 entry criteria measurable. The criteria are: at least 20 merged agent PRs, a CI first-pass green rate of at least 70%, no Warden bypass found, and "Ledger dashboard live" ([ADR-0008](../decisions/0008-autonomy-phases-and-risk-based-merge-policy.md)).

Today every hook writes one line to `<worktree>/.panopticon/wardens.log.jsonl` ([wardens-core spec](2026-11-04-wardens-core.md), "JSONL verdict log"). Those lines are per worktree. They are lost on `worktree remove`, and nothing joins them with GitHub outcomes.

v0 adds two things:

1. A durable, append-only JSONL file outside every worktree: `~/.local/state/panopticon/ledger/<project>/events.jsonl`. Every `wardens hook` invocation appends one record to it.
2. A command `wardens ledger report` that reads that file and GitHub, and prints the metrics and one result line per phase-1 criterion.

Krzysztof's decisions on #98 (2026-11-10) are binding here:

- A JSONL Ledger v0 lands before Postgres. This amends the v0 wording of [ADR-0010](../decisions/0010-the-ledger-and-observability.md). The decision-log row belongs to #101, not to this spec.
- For the phase 0 to 1 entry, the Markdown and JSON output of `wardens ledger report` counts as "Ledger dashboard live". Grafana on Postgres stays the later target.

The record keeps the ADR-0010 shape (`run`, `event`, `outcome`), so a later import into Postgres is a mechanical mapping (Plan, "Postgres import mapping").

Out of scope: Postgres tables, OTLP export, Grafana, cost and token usage, `wardens check` invocations (only `wardens hook` writes to the Ledger), and content capture of any kind.

The Ledger is not protective. Its write cannot change a verdict, with one exception stated in Plan ("Write path and failure"): a filesystem that hangs makes the hook time out, and the tool then blocks the action (C-03). The Ledger is also not tamper-proof: agents run under Krzysztof's UID and can reach the file by means that ring 0 does not see (Plan, "Trust and integrity").

## Acceptance criteria (EARS)

Each criterion names its enforcer. "Wardens test" means a Vitest case in `wardens-test` (CI) and `pnpm check`.

### Event writing

- WHEN a `wardens hook` invocation finishes with a verdict, The Charter loaded, and its `ledger.sink` contains `jsonl`, THE SYSTEM SHALL append exactly one record, as defined in Plan ("Event record"), to `~/.local/state/panopticon/ledger/<project>/events.jsonl`. *Enforced by:* Wardens test.
- WHEN a `wardens hook` invocation finishes without a loaded Charter (Charter invalid, no trusted primary, or no git toplevel), THE SYSTEM SHALL append exactly one record to `~/.local/state/panopticon/ledger/_unknown/events.jsonl`, without consulting `ledger.sink`. *Enforced by:* Wardens test, one case per path.
- WHEN the hook event is `SessionStart` (Claude Code) or `sessionStart` (Cursor), THE SYSTEM SHALL write that record with `record: "run_start"`. *Enforced by:* Wardens test.
- WHEN the hook event is `Stop` (Claude Code) or `stop` (Cursor), THE SYSTEM SHALL write that record with `record: "run_end"` and an `outcome` of `dod_green`, `dod_red`, `loop_limit`, `not_run` or `engine`, per Plan ("Stop outcome"). *Enforced by:* Wardens test, one case per outcome.
- WHEN any other hook event finishes, THE SYSTEM SHALL write that record with `record: "event"`. *Enforced by:* Wardens test.
- WHILE The Charter loaded and its `ledger.sink` does not contain `jsonl`, THE SYSTEM SHALL write no Ledger record and SHALL behave exactly as before this change. *Enforced by:* Wardens test.
- WHEN `wardens check` runs, THE SYSTEM SHALL write no Ledger record. *Enforced by:* Wardens test.
- THE SYSTEM SHALL write each record as one `JSON.stringify` line of at most 4096 bytes, including the final newline, with one `write` call on a descriptor opened with `O_WRONLY | O_APPEND | O_CREAT | O_NOFOLLOW | O_NONBLOCK`. *Enforced by:* Wardens test (size cap); single call by code review and the concurrency test.
- IF the opened file is not a regular file, has a link count other than 1, or is not owned by the current UID, THEN THE SYSTEM SHALL close it without writing and record the failure. *Enforced by:* Wardens test with a FIFO, a hard link and a symlink at the file path.
- IF `panopticon`, `ledger` or `<project>` under `~/.local/state/` is a symlink, is not a directory, is not owned by the current UID, or is not mode `0700`, THEN THE SYSTEM SHALL write nothing and record the failure. *Enforced by:* Wardens test, one case per reason.

### No content

- THE SYSTEM SHALL write only the keys listed in Plan ("Event record"). A strict zod schema SHALL reject any other key before the write. *Enforced by:* Wardens test that compares the key set of a written record with the schema.
- THE SYSTEM SHALL NOT write a prompt, file content, command text, path, path argument, MCP argument, C-30 message, `replacement` or absolute directory to the Ledger file (`ledger.capture_content: false`). *Enforced by:* Wardens test "no content" (Plan, "Tests").
- THE SYSTEM SHALL map every derived or payload string that fails its field rule to `null` (or `"other"` for `tool_name`) before validation, so that no agent-influenced value can make the record fail the schema. *Enforced by:* Wardens test per written string field (Plan, "Tests").
- WHEN The Charter sets `ledger.capture_content: true`, THE SYSTEM SHALL still write no content, and `wardens doctor` SHALL warn that v0 does not capture content. *Enforced by:* Wardens test.

### Write failure

- IF the Ledger record cannot be written for any reason, THEN THE SYSTEM SHALL return the same hook stdout and exit code, and SHALL append the same per-worktree log line, as it would with a working Ledger. *Enforced by:* Wardens test, one golden comparison per verdict class (allow, deny, ask, rewrite, each Stop outcome).
- IF the Ledger record cannot be written, THEN THE SYSTEM SHALL append one failure line to `<toplevel>/.panopticon/ledger-failures.jsonl` on a best-effort basis, and SHALL ignore any error from that append. *Enforced by:* Wardens test.
- THE SYSTEM SHALL NOT let a Ledger write turn an allow into a deny or a deny into an allow, and SHALL NOT retry, lock, `fsync`, start a child process or call the network inside the writer. *Enforced by:* Wardens test (throwing writer); no lock, retry, child or `fsync` by code review.
- WHEN `wardens doctor` runs outside `--ci`, THE SYSTEM SHALL run a `ledger` check that fails when any worktree of the primary checkout has a valid Ledger failure line from the last 7 days, and reports the count and the latest reason code. *Enforced by:* Wardens test of the doctor check.

### Ring 0 protection of the Ledger path

- WHEN an agent's Read, Edit, Write or Delete tool event names a path inside `~/.local/state/panopticon/ledger/`, THE SYSTEM SHALL deny with the existing rule `engine` and the message `Blocked by Warden engine: path escapes the worktree. Label the issue needs:human.`, also when a `paths.external` glob would match that path. *Enforced by:* Wardens test (ring 0), including a Charter fixture with an external glob that matches the Ledger directory.
- WHEN an agent's shell command has a path word that the existing shell path scan resolves inside `~/.local/state/panopticon/ledger/`, THE SYSTEM SHALL deny, also when a `paths.external` glob would match that path. *Enforced by:* Wardens test of the classes in Plan ("Ring-0 Ledger guard"); classes marked there as not yet enforced are not covered.
- WHEN `panopticon.charter.yaml` is validated, THE SYSTEM SHALL reject a `paths.external.read` or `paths.external.write` glob that matches one of the Ledger probe paths in Plan. *Enforced by:* `charter-validate`, Wardens test.

### Report

- WHEN a human runs `wardens ledger report --since <YYYY-MM-DD>`, THE SYSTEM SHALL print the report in Plan ("Report") as Markdown, and as JSON when `--json` is given. *Enforced by:* Wardens test against recorded `gh` fixtures.
- WHEN `wardens ledger report --backfill` runs, THE SYSTEM SHALL compute the GitHub-based metrics for all PRs merged to `main` since 2026-11-03, and SHALL mark each Ledger-based metric as unavailable for the dates before the first Ledger record. *Enforced by:* Wardens test.
- IF `--repo` does not match `^[A-Za-z0-9_.-]+/[A-Za-z0-9_.-]+$`, has a `.` or `..` segment, or a date value is not a real calendar date in the form `YYYY-MM-DD`, THEN THE SYSTEM SHALL exit 2 before any `gh` call. *Enforced by:* Wardens test of the input classes in Plan ("Report").
- THE SYSTEM SHALL call `gh` with an argv array and `shell: false`, never through a shell. *Enforced by:* Wardens test on the injected `gh` runner (asserts argv arrays); `spawnSync` options by code review.
- THE SYSTEM SHALL treat PR titles, PR bodies, commit messages and comments as untrusted data (C-20): it SHALL only count them or match them against the fixed patterns in Plan, and SHALL NOT print any part of them. *Enforced by:* Wardens test with a fixture whose title, body, commit message and comment carry a sentinel string and a Markdown injection; the sentinel must not appear in the report.
- THE SYSTEM SHALL print each result with its `basis` (`github`, `ledger` or `github+ledger`), and SHALL mark every result whose basis includes `ledger` as "agent-writable, unverified". *Enforced by:* Wardens test.
- THE SYSTEM SHALL print one line per phase-1 criterion with a result from Plan ("Phase-1 criteria"). *Enforced by:* Wardens test.
- IF a `gh` call fails, times out or returns JSON that does not parse, THEN THE SYSTEM SHALL print an error that names the call shape and the exit code, without `gh` stderr, exit 2, and SHALL NOT print a partial report. *Enforced by:* Wardens test.
- THE SYSTEM SHALL exit 0 when the report is printed, whatever the criterion results, and SHALL NOT exit 1. *Enforced by:* Wardens test.

### Tests

- THE SYSTEM SHALL contain Vitest tests for event writing, the no-content rule, write-failure behaviour, every failure reason, concurrent appends, partial lines, rotation and the total cap, the ring-0 Ledger guard and each report metric against recorded `gh` JSON fixtures. *Enforced by:* `wardens-test`.

## Plan

### Approach

1. A new module `wardens/src/ledger/` holds the record schema, the writer, the reader and the report. The record builder is a pure function of the finished verdict, the normalized event, the raw payload's `tool_name` and a few environment facts.
2. `runHook` in `wardens/src/engine.ts` passes a Ledger context to `commit()` (a new optional input). `runCheck` does not pass it, so `wardens check` never writes to the Ledger. `commit()` calls the writer after the per-worktree append, inside its own `try`/`catch`. The record describes the verdict that the tool is sent, including an `engine` deny caused by a failed per-worktree append.
3. `definitionOfDone` and `stopEngineFailure` in `wardens/src/dod.ts` return an explicit Stop outcome next to the verdict, so the Ledger does not parse C-30 messages.
4. `externalAllows` in `wardens/src/external.ts` never allows a path inside the Ledger directory. That one function judges outside paths for tool events (`normalizeHook`), shell path words (`secretReadGuard`) and shell write targets (`worktree-guard`), so all three end in their existing deny.
5. `wardens doctor` gains a `ledger` check.
6. `wardens ledger report` reads the Ledger files and calls `gh`.

### Ledger location and enablement

- Directory: `<home>/.local/state/panopticon/ledger/<project>/`. `<home>` is `trustedHome(env)` (`wardens/src/home.ts`). `XDG_STATE_HOME` is ignored, so the guard protects one fixed path.
- `<project>` is The Charter's `project` (`lunarhunt` today), read from the trusted primary, when The Charter loaded and the value matches `^[a-z0-9][a-z0-9-]{0,63}$`. Otherwise `<project>` is `_unknown`.
- A hook run without a loaded Charter writes to `_unknown` always: Charter invalid, `deps.primary === null` (no trusted primary), and the no-toplevel paths (`fail` with `toplevel: null`, `allowUnresolvedStop`), which run before any Charter load. These are the `engine` paths that C-06 and ADR-0010's "no silent paths" most need to see.
- A hook run with a loaded Charter writes only when `ledger.sink` contains `jsonl`. Today the value is `[postgres, otlp]`, so nothing is written to `<project>` until Krzysztof changes The Charter (Task 9). The schema already accepts any non-empty string in `sink`; no schema change is needed.
- `ledger.capture_content` is read only for the doctor warning. v0 never writes content.
- Files: `events.jsonl` (current) and `events-<YYYYMMDDTHHMMSSZ>-<pid>.jsonl` (rotated).

Permissions, checked by the writer on every write:

- `panopticon`, `ledger` and `<project>` under `~/.local/state/` are created with mode `0700` when missing.
- Each of those three components must be a directory, not a symlink (`lstat`), owned by the current UID, with mode `0700`.
- The file is opened with `O_WRONLY | O_APPEND | O_CREAT | O_NOFOLLOW | O_NONBLOCK` and mode `0600`. A symlink at the file path fails the open (`ELOOP`). `O_NONBLOCK` keeps the open of a FIFO or device from blocking.
- After the open, `fstat` on the descriptor must show a regular file with link count 1, owned by the current UID. Otherwise the writer closes it without writing.

These checks are best effort against a process with the same UID. Between the `lstat` of a directory and the `open`, another process can swap the directory for a symlink; Node has no `openat` to close that race. What they guarantee is narrower: a hook never writes into a FIFO, device or hard-linked file, and every line it writes is bounded and hygiene-filtered (below), so a redirected append carries no agent-chosen text beyond the filtered names.

### Event record

One JSON object per line, written with `JSON.stringify`. A zod `strictObject` validates it before the write. Every key is always present; "nullable" means the value may be `null`, never that the key is missing.

| Key | Type | Nullable | Source |
| --- | --- | --- | --- |
| `v` | `1` | no | constant schema version |
| `record` | `"run_start"` \| `"event"` \| `"run_end"` | no | from the hook event (Acceptance criteria, Event writing) |
| `ts` | string, ISO 8601 UTC with milliseconds | no | `deps.now()` when the verdict is final, same instant as the per-worktree line |
| `project` | string | no | see "Ledger location" |
| `session_id` | string | yes | normalized `session_id`; on a failure path before normalization, raw `session_id`, else raw `conversation_id`, when it is a string |
| `run_id` | string, 32 lowercase hex | yes | first 16 bytes of SHA-256 of `<tool>:<session_id>`; `null` when `tool` or `session_id` is `null` |
| `tool` | `"claude"` \| `"cursor"` | yes | `--tool` when it is a known tool, else `null` |
| `role` | Charter role name | yes | `PANOPTICON_ROLE` when it equals one of `overseer`, `spec-writer`, `implementer`, `reviewer`, `sentinel`, `debugger`; else `null` |
| `model` | string | yes | normalized `model` (payload string only) |
| `agent_type` | string | yes | normalized `agent` (Claude `agent_type`) |
| `event` | string | yes | `--event` when it is a hook event name that `mapPayload` maps, `"other"` for any other value, `null` when absent |
| `tool_name` | string | yes | raw payload `tool_name` when it is a string; `null` for events without one |
| `action` | normalized action | yes | normalized `action`, `null` before normalization |
| `decision` | `allow` \| `deny` \| `ask` \| `rewrite` | no | finished verdict `decision` |
| `rendered` | `allow` \| `deny` \| `ask` \| `rewrite` | no | finished verdict `rendered` |
| `warden_rule_id` | string | yes | finished verdict `rule`; `null` when it is `none` |
| `outcome` | Stop outcome | yes | `run_end` only; `null` on other records |
| `interactive` | boolean | no | normalized `interactive`, `false` before normalization |
| `worktree` | string | yes | basename of the git toplevel; `null` without a toplevel |
| `primary` | boolean | no | `true` when `classifyCwd` returns `kind: "primary"`; `false` otherwise, including without a toplevel |
| `branch` | string | yes | see "Derived fields" |
| `issue` | integer, 1 to 2147483647 | yes | see "Derived fields" |
| `duration_ms` | integer ≥ 0 | no | same value as the per-worktree line: verdict time minus start time, before the Ledger write |

Field rules. A value that fails its rule is written as `null`; `tool_name` is written as `"other"`.

- `session_id`, `agent_type`, `tool_name`, `branch`, `worktree`: `^[A-Za-z0-9._:/@-]{1,128}$`.
- `model`: `^[A-Za-z0-9._:/@\[\]-]{1,64}$`, so a bracketed model id such as `example-model[1m]` is kept.
- All six: a value that also matches a token shape (`ghp_`, `gho_`, `ghs_`, `ghu_`, `github_pat_`, `sk-`, `xox` followed by at least 16 more characters) is written as `null`. This is a best-effort filter.
- `issue`: an integer from 1 to 2147483647. A larger value, or a digit run that does not convert exactly, gives `null`.

Residual: identifiers that agents choose (branch, worktree, and to a degree session and tool names) are kept verbatim when they pass these rules. A secret shaped as a plain identifier passes. These fields are names, not content, but they are not a safe place for a secret either.

Unknown fields per tool today:

| Key | Claude Code | Cursor (frozen, ADR-0017) |
| --- | --- | --- |
| `role` | always `null` in v0: no launch path sets `PANOPTICON_ROLE` yet; the key exists for a later launcher | always `null` |
| `model` | only when the payload has a string `model`; Task 4 records which Claude events carry it | present on the recorded payloads |
| `agent_type` | set for subagent tool calls only | always `null` |
| `tool_name` | set on `PreToolUse` and `PostToolUse`; `null` on `SessionStart` and `Stop` | set on `preToolUse`; `null` on `beforeShellExecution`, `beforeReadFile`, `beforeMCPExecution`, `afterFileEdit`, `sessionStart`, `stop` |
| `session_id` | always on mapped events | `session_id`, else `conversation_id` |
| `issue` | `null` in subagent worktrees whose branch is still `worktree-agent-<hash>` and that have no task file | same rule |

The report resolves a session's model from its first `run_start` record when tool records leave it `null`.

### Derived fields and why they are not content

- `worktree` is the last path segment of the git toplevel, for example `98-ledger-v0-spec` or `agent-1a2b3c`. The absolute path, which holds the home directory and user name, is never written.
- `branch` and `primary` come from `classifyCwd(toplevel)` in `wardens/src/git.ts`. It runs `git rev-parse` twice and `git symbolic-ref --short -q HEAD`, with no timeout of its own, like the `worktree-guard` call that already runs on every hook. Task 4 reuses the result when `worktree-guard` has already computed it for the same directory. A detached head or a git failure gives `branch: null`.
- `issue` is the `issue` of a valid, integrity-checked `.panopticon/task.json` (the `TaskState` the hook already loaded); else the number in a branch matching `^[a-z]+/([1-9][0-9]{0,9})-`, kept only when it is at most 2147483647; else `null`.

These are names, not content. Branch names and issue numbers are public on GitHub once pushed. The worktree name is the issue slug or a random hash. None of them carries a prompt, a file body, a command or a path argument. They are still agent-chosen strings, so the field rules above apply.

### Stop outcome

One rule decides, in this order:

1. If the finished verdict's rule is `engine`, the outcome is `engine`. This covers a rule that threw on a Stop, the third red Stop caused by an engine failure (`stopEngineFailure` returns an allow with rule `engine` at `RED_LIMIT`), the unresolved-toplevel allow, and a failed per-worktree append that turned the Stop into an `engine` deny.
2. Otherwise the outcome tag from `definitionOfDone`:

| Outcome | When |
| --- | --- |
| `dod_green` | allowed because `pnpm check` ran green, or the fingerprint equals the last green one |
| `dod_red` | denied: red or timed out, below the limit |
| `loop_limit` | the third red Stop in a session caused by `pnpm check`: allowed with the `needs:human` line |
| `not_run` | the check did not run: nothing to deliver, or Cursor `status` is not `completed` |

A denied Stop does not end the session. A session can therefore have several `run_end` records (for example `dod_red`, then `dod_green`). Its final outcome is the outcome of its last `run_end` by `ts`.

`usage_limit` is reserved for #99. v0 does not write it. #99's spec defines the write point.

### Write path and failure

Order inside `commit()`:

1. Finish the verdict, as today.
2. Append the per-worktree line, as today. If that throws, the verdict becomes `engine` deny, as today.
3. If the Ledger context is present and the rules in "Ledger location" say to write, build and append the record of the verdict from step 1 or 2, inside `try`/`catch`.
4. Return the verdict from step 1 or 2. Step 3 cannot change it.

The no-toplevel paths write a record with `worktree: null`, `branch: null`, `issue: null` and `primary: false` to `_unknown`.

Writer budget. The writer does at most: three `lstat`, up to three `mkdir`, one `open`, one `fstat`, one 1-byte `pread`, one `write`, one `close`, one directory size scan of `<project>` on rotation only, and at most one `rename`. No lock, retry, `fsync`, child process or network call. The `git` calls for `branch` happen in the record builder, not in the writer.

Hang. With `O_NONBLOCK` and the regular-file check, a FIFO or device at the file path cannot block the open. A hung filesystem can still block the `write`. Then the hook does not return before its timeout (10 s, or 900 s for Stop), and the tool's fail-closed setting (`onFailure: "block"`, ADR-0005) blocks the action. This is the one way the Ledger can change an outcome: an allow becomes a block, never the reverse. The per-worktree append already has the same exposure. Hook timeouts are unchanged.

Failure line, `<toplevel>/.panopticon/ledger-failures.jsonl`:

```json
{"ts":"2026-11-20T08:00:00.000Z","project":"lunarhunt","reason":"open"}
```

- `reason` is one of `home_unresolved`, `not_directory`, `symlink`, `not_owned`, `bad_mode`, `mkdir`, `open`, `not_regular`, `link_count`, `write`, `too_long`, `schema`, `rotate`, `cap`. No error text, path or errno string is written.
- The failure file is opened with the same flags and checks as the Ledger file, and the line is not written once the file reaches 1 MiB.
- Without a toplevel the failure line is skipped. Any error on this append is ignored.

### Concurrent appends, partial lines, rotation and cap

Several sessions in several worktrees append to the same file.

- Each record is one `write` of the whole line on an `O_APPEND` descriptor. On local APFS and ext4, such a write moves the offset and writes the bytes as one step, so whole lines from different processes do not interleave. POSIX does not promise this for regular files. Network filesystems are not supported. The doctor check warns when the directory is not on a local filesystem, where the platform can tell.
- Line cap: 4096 bytes with the newline. With the field rules a record stays well below that. A record over the cap is not written and fails with `too_long`.
- Partial line from an earlier crash or a full disk: before writing, the writer reads the last byte of the file (`fstat` plus a 1-byte `pread`). When the file is non-empty and that byte is not `\n`, it prefixes its line with `\n`. A race can add an empty line; the reader ignores empty lines.
- A short `write` (fewer bytes than the line) is a `write` failure. The writer does not try to complete it.
- Rotation: when `fstat` shows `events.jsonl` at or above the rotation size (64 MiB), the writer renames it to `events-<UTC time>-<pid>.jsonl` and opens a new `events.jsonl`. A writer that still holds the old descriptor finishes into the renamed file; no line is lost. Two writers that rotate at once produce one extra small rotated file; this is accepted. A failed rename is `rotate` and the line is not written.
- Total cap: when rotating, the writer sums the sizes of the files in `<project>`. At or above 1 GiB it writes nothing more and fails with `cap`, until a human removes rotated files. A loop of denied calls therefore cannot fill the disk through the Ledger.
- The rotation size and the total cap are writer dependencies with these defaults, so tests can inject small values.
- Reader: opens only regular files (`lstat`, no symlink), streams line by line, and stops at the total cap. It ignores empty lines, skips a line that does not parse as JSON or does not match the schema and counts it as `malformed`, and counts a last line without `\n` as `partial`. The report header shows both counts.
- Retention: v0 deletes nothing (open question 2). At an estimated 300 bytes per record and a few thousand hook calls per day, the cap lasts many months.

### Trust and integrity

The Ledger file lives in Krzysztof's home directory. Hooks and agents run under the same UID. Ring 0 is a guard rail, not a sandbox. v0 has no tamper protection and does not claim any. Every point in this section is **not yet enforced** unless it names an enforcer.

What an agent could do if it reaches the file by a path ring 0 does not see (an interpreter such as `node -e` or `python -c`, a script it wrote, variable indirection, a glob word the scan does not resolve):

- **Forge** records: add a `run_start` for its session, add `run_end` with `dod_green`, add `event` records on a branch, change `tool`, `role` or `model`.
- **Delete** lines, for example its own deny records.
- **Truncate** or remove `events.jsonl` and the rotated files.
- **Write** into `_unknown` or another project's directory.
- **Pre-create** the directories or the file with other owners or modes, which turns every later write into a failure (the doctor check then fails).

What an agent can do without touching the file:

- **Suppress its own records by making the write fail.** The field rules leave no value that fails the schema, and the line cap cannot be reached, so the remaining ways are file-level: a FIFO, a hard link, a symlink, a wrong mode or a filled cap. Each one is a failure line and a doctor `fail`, not a silent loss. Enforced by the writer checks and the doctor `ledger` check.
- **Leave no record at all.** A session whose hooks never ran (hooks disabled, `disableAllHooks`, a harness without these hooks, a nested `claude -p` with other settings) writes nothing. Only B6 sees this, at PR level, and B6 is masked by a single record on the same branch, forged or from an unrelated session.
- **Move attribution.** It can rename its branch (`git branch -m` is not denied) and set `PANOPTICON_ROLE` for a nested `claude -p` it starts. Its own `task.json` is covered by the integrity hash.
- **Raise the first-pass CI rate.** It can push a trivial green commit, open the PR on it, and push the real work afterwards. M2 then counts the trivial commit.

Metrics that tampering with the file would change:

| Metric | Effect |
| --- | --- |
| Warden blocks per task (M4) | lowered by deleted deny records; moved by a renamed branch |
| Sessions without `run_start` (B4) | hidden by a forged `run_start` |
| `engine` allows (B5) and the `engine` deny rate | hidden by deletion |
| Merged agent PRs without Ledger records (B6) | hidden by one forged record on the branch |
| Run outcomes, `loop_limit` counts (M8) | forged or hidden |
| Runs with `tool != claude` (M7, Ledger half) | hidden by an edited `tool` |
| Usage-limit stops per day (M6, once #99 writes them) | forged or hidden |
| "Ledger dashboard live" | made to pass by forged sessions, or made `incomplete` by truncation |

Metrics computed from GitHub alone, which the Ledger file cannot change:

- merged agent PRs (M1);
- CI first-pass green rate (M2): check runs come from the GitHub Actions app; a user token can create commit statuses but not check runs, and the report reads check runs only;
- merged agent PRs with a required check not green at merge (B1);
- PR commits without an `Agent:` trailer (B2) and commits on `main` without a merged PR (B3);
- review rounds per PR (M5).

These are not tamper-proof either. Agents use Krzysztof's `gh` token (#94, decision 5). An agent chooses its own trailer text (C-27 is self-reported), can post a comment that looks like a review-round header, and can shape its first push (above). The report prints the basis of every result and never says "verified".

Detection, not prevention:

- The per-worktree `.panopticon/wardens.log.jsonl` is a second copy while the worktree exists. v0 does not cross-check it (follow-up).
- The doctor `ledger` check fails on wrong owner, wrong mode, a symlink, a non-regular file or a valid failure line, and warns on `malformed` or `partial` lines.

The control that would put the file out of reach of agent shell commands is the Claude Code sandbox from PR #70: `denyWrite` and `denyRead` entries that cover the Ledger directory. Hooks run outside the sandbox (PR #70, "Where hooks run"), so they can still write. The entry is generated from The Charter by `wardens sync`; the Charter change and the sync are Krzysztof's (Task 9).

### Ring-0 Ledger guard

Purpose of the read deny: the raw file lists every session's ids, branches and timings across all worktrees; denying reads keeps an agent from copying real session ids into forged records and keeps other tasks' metadata out of its context, while the filtered report stays the intended reader.

How it works:

- `externalAllows` (`wardens/src/external.ts`) returns `null` for any target inside `<home>/.local/state/panopticon/ledger/`. The target is the realpath-normalized path it already computes, compared case-folded where the volume is case-insensitive (`caseInsensitiveAt`), like the glob match.
- Tool events: `normalizeHook` already denies an outside path with rule `engine` ("path escapes the worktree") unless `externalAllows` returns a path. With the change, no Charter glob can open the Ledger directory. The verdict stays the existing `engine` escape deny.
- Shell: `secretReadGuard` throws the same "path escapes the worktree" failure for an outside path word that `externalAllows` rejects, except for glued option values (class table); `evaluateRules` returns that throw as an `engine` deny. `worktree-guard`'s external-write check uses the same function. A `cd` out of the worktree is already a `command-guard` deny ("the command could not be parsed safely", `expansionDeny`).
- No new rule and no raw-text pattern. Text that only mentions the path (a commit message, an `rg` pattern) is not denied.
- `charter-validate` rejects a `paths.external` glob that matches any probe path: `~/.local/state/panopticon/ledger`, `~/.local/state/panopticon/ledger/lunarhunt/events.jsonl`, `~/.local/state/panopticon/ledger/lunarhunt/events-20261120T000000Z-1.jsonl` and `~/.local/state/panopticon/ledger/_unknown/events.jsonl`. Probes are matched with `~` expanded both to the trusted home (when it resolves) and to a fixed synthetic home, so `~/**`, `**`, `/**` and `~/.local/**` are rejected on every machine. This is defence in depth; the runtime exclusion is the control.

### Report

Command: `wardens ledger report (--since <YYYY-MM-DD> | --backfill) [--until <YYYY-MM-DD>] [--json] [--repo <owner/repo>]`.

Inputs:

- Dates are UTC days. `--since` is inclusive from 00:00. `--until` is inclusive to 23:59:59.999 and defaults to now. `--backfill` sets `--since 2026-11-03`.
- The repository comes from `--repo`, else from the issue-repository sidecar written by `wardens sync` (`readRepo`), else the command fails. The header always prints the repository, and a warning line when `--repo` differs from the sidecar. The repository and the window come from the human or the sidecar; there is no flag that names a Ledger path.
- Input validation, before any `gh` call, exit 2 on failure: `--repo` matches `^[A-Za-z0-9_.-]+/[A-Za-z0-9_.-]+$` with no `.` or `..` segment; each date matches `^[0-9]{4}-[0-9]{2}-[0-9]{2}$` and is a real calendar date; `--since` is not after `--until`. Tests cover these classes: query or fragment characters, an extra path segment, a traversal segment, percent-encoded characters, whitespace, an impossible date and a reversed window.
- Ledger input: every `events*.jsonl` file under `ledger/<project>/` and `ledger/_unknown/`. The report opens them in its own process; the ring-0 guard judges an agent's tool calls, not the files a Wardens process opens.
- A PR is in the window when its `merged_at` is in the window. A Ledger record is in the window when its `ts` is.

#### `gh` calls

All calls go through one injected runner: `spawnSync("gh", argv, { shell: false, timeout: 60_000 })`. Only these argv shapes are used. `{repo}`, numbers and SHAs are validated values; `{head_ref}` is URL-encoded and must pass the `branch` field rule, otherwise the PR's first SHA is `unknown` and call 3 is skipped.

1. `["api", "--paginate", "--slurp", "repos/{repo}/pulls?state=closed&base=main&per_page=100"]`, keeping PRs with `merged_at` in the window.
2. `["api", "--paginate", "--slurp", "repos/{repo}/pulls/{n}/commits?per_page=100"]`.
3. `["api", "--paginate", "--slurp", "repos/{repo}/actions/runs?event=pull_request&branch={head_ref}&per_page=100"]`.
4. `["api", "--paginate", "--slurp", "repos/{repo}/commits/{sha}/check-runs?filter=all&per_page=100"]`. `filter=all` returns every run, not only the latest per name.
5. `["api", "--paginate", "--slurp", "repos/{repo}/issues/{n}/comments?per_page=100"]`.
6. `["api", "--paginate", "--slurp", "repos/{repo}/commits?sha=main&since={since}T00:00:00Z&until={until}T23:59:59Z&per_page=100"]`.

`--slurp` makes `gh` print one JSON array of pages. For calls 1, 2, 5 and 6 each page is an array and the parser concatenates them. For calls 3 and 4 each page is an object, and the parser concatenates its `workflow_runs` or `check_runs` member. Each response is parsed with zod; only the fields the metrics need are kept, and titles and bodies are dropped at parse time. A `gh` without `--slurp` fails the call (exit 2).

Errors name the call shape (for example `call 4 (check-runs)`) and the `gh` exit code. `gh` stderr is never printed: it can carry tokens or untrusted text.

#### Fixed patterns

- Agent trailer: a commit message line matching `^Agent: (claude|cursor) \(.+\)$`, the same pattern as `agent-trailer` (`wardens/src/trailer.ts`). Only the tool group is used. The model text is never printed.
- Review-round header (github-writing skill, ADR-0016 D9): the first line of a PR comment matching `^\*\*(Reviewer|Sentinel) round ([1-9][0-9]?): [0-9]+ blocking, [0-9]+ non-blocking\*\* at [0-9a-f]{7,40}`.
- Required checks: check runs named `check`, `contract`, `charter-drift`, `wardens-test` whose `app.slug` is `github-actions`. Commit statuses are ignored.

#### Metrics

Each metric is defined by inputs, filter, formula and edge cases. Each result carries its `basis`.

**M1. Merged agent PRs.** Basis: `github`.
- Inputs: calls 1 and 2.
- Filter: PRs merged into `main` in the window, with at least one PR commit (call 2) that has an agent trailer.
- Formula: the count. The JSON lists PR numbers and the trailer tools seen.
- Edge cases: the commits endpoint returns at most 250 commits; a PR at that limit is marked `commits_truncated`. Renovate PRs have no trailer and are not agent PRs. A human commit with a trailer makes its PR an agent PR (self-reported, see "Trust and integrity").

**M2. CI first-pass green rate.** Basis: `github`.
- Inputs: M1 PRs, calls 3 and 4.
- First head SHA: the `head_sha` of the earliest `pull_request` workflow run (by `created_at`, then `id`) whose `pull_requests` contains the PR number. If no run lists the PR, the earliest run on its head branch created between the PR's `created_at` and `merged_at`. If there is none, the first SHA is `unknown`.
- Applicable checks for M2: the required names with at least one check run on the first head SHA. A PR opened before a check existed is judged on the checks that ran on its first head SHA; a check added later is not held against it here (B1 still judges the final SHA).
- First-pass green: for each applicable check, the earliest check run with that name on the first head SHA (by `started_at`, then `id`, from call 4 with `filter=all`) has `conclusion: success`. A rerun does not count. `cancelled`, `skipped`, `neutral`, `timed_out`, `failure`, `action_required` and still running count as not green.
- Formula: `green` PRs over `n` M1 PRs with a known first SHA and at least one applicable check. The threshold test is `green * 10 >= n * 7`, on integers. The rate is printed as a percentage with one decimal, and as `green/n`.
- Edge cases: PRs with `unknown` first SHA or no applicable check are excluded from `n` and listed. `n = 0` makes the rate `n/a`.

**M3. Warden bypass candidates.** A candidate is a fact for a human to review, not a finding. Each class is listed with its count, its basis and its items.

The #98 criterion "agent commits on `main` without an `Agent:` trailer" maps to B2 and B3. `main` takes squash merges only (decision log), so the squash commit's message is not used; the trailer is looked up in the PR's own commits (B2), and a commit on `main` that no merged PR produced is B3.

- **B1. Merged with a required check not green.** Basis: `github`. Applicable checks for B1: the required names with at least one check run on the first or the final head SHA. For each, take the latest check run on the final head SHA (`head.sha` from call 1) by `started_at`, then `id`, in any status. It counts as green only when it is completed with `conclusion: success`. A missing run, or one not completed, is not green. A PR with any non-green applicable check is a candidate.
- **B2. PR commits without a trailer.** Basis: `github+ledger`. Commits of M1 PRs that have one parent and no agent trailer. Merge commits from `main` into the branch are skipped. When Ledger data covers the commit time, each item is marked `in_session: true` if its committer date lies between the first and last record of a session on the PR's head branch. Human fix-up commits appear here by design.
- **B3. Commits on `main` without a merged PR.** Basis: `github`. Commits from call 6 whose SHA is not the `merge_commit_sha` of any merged PR from call 1.
- **B4. Sessions without `run_start`.** Basis: `ledger`. Ledger sessions, keyed by `(tool, session_id)`, that have at least one `event` record in the window and no `run_start` record at any time. Records with `session_id: null` are counted on their own line.
- **B5. `engine` allows.** Basis: `ledger`. Records with `warden_rule_id: "engine"` and `rendered: "allow"`: the unresolved-toplevel Stop and the engine-caused loop limit. These are the cases where the engine let an action or a stop through without judging it. This is the class behind the #98 wording "decision: engine": in the engine, `engine` is a rule id, not a decision value.
- **B6. Merged agent PRs without Ledger records.** Basis: `github+ledger`. M1 PRs created after the first Ledger record whose head branch has no Ledger record. This is ADR-0010's "sessions without hook events" check at PR level.

Information, not a candidate class: `engine` denies (fail-closed denials such as out-of-worktree paths and unmapped events) are listed with their count per UTC day, their count per session-hour, and the five sessions with the most, so a flood is visible. Basis: `ledger`.

**M4. Warden blocks per task.** Basis: `ledger`.
- Input: Ledger `event` records in the window.
- Task key: `issue`, else `branch`, else `worktree`, else `unattributed`.
- Formula per task: the number of records with `rendered: "deny"`, split by `warden_rule_id`. `ask` and `rewrite` are counted in their own columns. Stop records are not blocks; their outcomes appear under M8.
- Summary: the median and maximum over tasks with at least one record. For an even count the median is the mean of the two middle values, printed with one decimal.

**M5. Review rounds per PR.** Basis: `github`.
- Inputs: M1 PRs, call 5.
- Formula per PR and role (`Reviewer`, `Sentinel`): the number of distinct round numbers in matching headers. A PR without headers has `null` for that role, not 0.
- Summary: the count of PRs with headers, the mean and maximum per role, and the PRs above 2 rounds for one role. The limit 2 is ADR-0016 D9's value, hard-coded in v0 because the Charter key (`review.max_rounds`) does not exist yet; the report reads the key once the schema has it.
- Edge cases: all comments are posted with Krzysztof's token, so authorship cannot be checked. A header-shaped comment counts whoever wrote it.

**M6. Usage-limit stops per day.** Basis: `ledger`.
- Input: Ledger `run_end` records with `outcome: "usage_limit"`, grouped by UTC day of `ts`.
- Availability: always `unavailable` in v0. `mapPayload` does not map `Notification`, and nothing writes `usage_limit` until #99 adds both. The metric becomes available when the window contains a record with `event: "Notification"`. Until then the report does not print 0.

**M7. Runs with `tool != claude` (ADR-0017).** Basis: `github+ledger`.
- Ledger: sessions whose records have `tool: "cursor"` or `tool: null`.
- GitHub: M1 PRs with a `cursor` trailer.
- Formula: two counts with items. Not a phase-1 criterion; a flag for Krzysztof.

**M8. Run outcomes.** Basis: `ledger`. Final outcome per session (last `run_end`), counted by outcome, and sessions with no `run_end`.

Header lines: window, repository, Ledger coverage start (first record `ts`, or "none"), files read, `malformed` and `partial` line counts, and the count of `_unknown` records.

#### Backfill

`--backfill` computes M1, M2, B1, B2 (without `in_session` marks), B3, M5 and the GitHub half of M7 for PRs merged since 2026-11-03. Unavailable for dates before the first Ledger record: B4, B5, B6, the `engine` deny information, M4, M6, the Ledger half of M7, M8 and the `in_session` mark. The report names them in an "Unavailable before <date>" line. Review-round headers exist only from the github-writing shape onward; earlier PRs have `null` rounds.

- A payload with a `prompt` field holding `SENTINEL_PROMPT_9f1c`, and a `cwd` under a temporary home whose name holds `SENTINEL_HOME_9f1c`.

Field-rule test, for each written string field (`session_id`, `model`, `agent_type`, `tool_name`, `branch`, `worktree`): a value with a newline, a NUL, more than the length limit, non-ASCII letters, a backtick, and a token-shaped value. Each is written as `null` (or `"other"`), and the record still validates. Plus: a bracketed model id is kept; a branch `feat/<eleven digits>-x` gives `issue: null`; a branch made of an instruction-like sentence is filtered or printed cut in a code span by the report.

Write-failure test. The same payloads plus one Stop per outcome run twice: with a working writer and with a writer that throws. Stdout, exit code and the per-worktree line (without `ts` and `duration_ms`) must be byte-equal between the two runs. Further cases, one per failure reason: FIFO at the file path (the open returns without blocking and the reason is `not_regular` or `open`), hard link (`link_count`), symlink file (`open`), symlink directory (`symlink`), wrong owner where the test can simulate it (`not_owned`), mode `0755` (`bad_mode`), injected small rotation size (`rotate` path), injected small total cap (`cap`).

Concurrency test. 8 child processes append 500 records each to one file. The reader finds 4000 parseable lines, 0 `malformed` and 0 `partial`.

Cursor. ADR-0017 D2 freezes new Cursor fixtures and tests. Cursor cases use the existing recorded fixtures only.
