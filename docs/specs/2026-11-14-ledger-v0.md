# Ledger v0: run events in JSONL and a phase-1 criteria report

## Goal and context

Issue [#98](https://github.com/LUNARITYai/lunarhunt/issues/98) makes the ADR-0008 phase-1 entry criteria measurable. The criteria are: at least 20 merged agent PRs, a CI first-pass green rate of at least 70%, no Warden bypass found, and "Ledger dashboard live" ([ADR-0008](../decisions/0008-autonomy-phases-and-risk-based-merge-policy.md)).

Today every hook writes one line to `<worktree>/.panopticon/wardens.log.jsonl` ([wardens-core spec](2026-11-04-wardens-core.md), "JSONL verdict log"). Those lines are per worktree. They are lost on `worktree remove`, and nothing joins them with GitHub outcomes.

v0 adds two things:

1. A durable, append-only JSONL file outside every worktree: `~/.local/state/panopticon/ledger/<project>/events.jsonl`. Every `wardens hook` invocation appends one record to it.
2. A command `wardens ledger report` that reads that file and GitHub, and prints the metrics and a pass or fail line per phase-1 criterion.

Krzysztof's decisions on #98 (2026-11-10) are binding here:

- A JSONL Ledger v0 lands before Postgres. This amends the v0 wording of [ADR-0010](../decisions/0010-the-ledger-and-observability.md). The decision-log row belongs to #101, not to this spec.
- For the phase 0 to 1 entry, the Markdown and JSON output of `wardens ledger report` counts as "Ledger dashboard live". Grafana on Postgres stays the later target.

The record keeps the ADR-0010 shape (`run`, `event`, `outcome`), so a later import into Postgres is a mechanical mapping (Plan, "Postgres import mapping").

Out of scope: Postgres tables, OTLP export, Grafana, cost and token usage, `wardens check` invocations (only `wardens hook` writes to the Ledger), and content capture of any kind.

The Ledger is not protective. A Ledger write never changes a verdict (C-03 applies to protective Wardens only). The Ledger is also not tamper-proof: agents run under Krzysztof's UID and can reach the file by means that ring 0 does not see (Plan, "Trust and integrity").

## Acceptance criteria (EARS)

Each criterion names its enforcer. "Wardens test" means a Vitest case in `wardens-test` (CI) and `pnpm check`.

### Event writing

- WHEN a `wardens hook` invocation finishes with a verdict and The Charter `ledger.sink` contains `jsonl`, THE SYSTEM SHALL append exactly one record, as defined in Plan ("Event record"), to `~/.local/state/panopticon/ledger/<project>/events.jsonl`. *Enforced by:* Wardens test.
- WHEN the hook event is `SessionStart` (Claude Code) or `sessionStart` (Cursor), THE SYSTEM SHALL write that record with `record: "run_start"`. *Enforced by:* Wardens test.
- WHEN the hook event is `Stop` (Claude Code) or `stop` (Cursor), THE SYSTEM SHALL write that record with `record: "run_end"` and an `outcome` of `dod_green`, `dod_red`, `loop_limit`, `not_run` or `engine`, per Plan ("Stop outcome"). *Enforced by:* Wardens test, one case per outcome.
- WHEN any other hook event finishes, THE SYSTEM SHALL write that record with `record: "event"`. *Enforced by:* Wardens test.
- WHILE `ledger.sink` does not contain `jsonl`, THE SYSTEM SHALL write no Ledger record and SHALL behave exactly as before this change. *Enforced by:* Wardens test.
- THE SYSTEM SHALL write each record as one `JSON.stringify` line of at most 4096 bytes, including the final newline, with one `write` call on a descriptor opened with `O_APPEND | O_CREAT | O_NOFOLLOW`. *Enforced by:* Wardens test (size cap, symlink refusal); the single-call append is checked by code review and a concurrency test (Plan, "Concurrent appends").

### No content

- THE SYSTEM SHALL write only the keys listed in Plan ("Event record"). A strict zod schema SHALL reject any other key before the write. *Enforced by:* Wardens test that compares the key set of a written record with the schema.
- THE SYSTEM SHALL NOT write a prompt, file content, command text, path, path argument, MCP argument, C-30 message, `replacement` or absolute directory to the Ledger file (`ledger.capture_content: false`). *Enforced by:* Wardens test "no content" (Plan, "Tests").
- WHEN The Charter sets `ledger.capture_content: true`, THE SYSTEM SHALL still write no content, and `wardens doctor` SHALL warn that v0 does not capture content. *Enforced by:* Wardens test.

### Write failure

- IF the Ledger record cannot be written for any reason, THEN THE SYSTEM SHALL return the same hook stdout and exit code, and SHALL append the same per-worktree log line, as it would with a working Ledger. *Enforced by:* Wardens test, one golden comparison per verdict class (allow, deny, ask, rewrite, each Stop outcome).
- IF the Ledger record cannot be written, THEN THE SYSTEM SHALL append one failure line to `<toplevel>/.panopticon/ledger-failures.jsonl` on a best-effort basis, and SHALL ignore any error from that append. *Enforced by:* Wardens test.
- THE SYSTEM SHALL NOT let a Ledger write turn an allow into a deny or a deny into an allow, and SHALL NOT retry, lock, `fsync` or call the network while writing. *Enforced by:* Wardens test (throwing writer); no lock, retry or `fsync` by code review.
- WHEN `wardens doctor` runs outside `--ci`, THE SYSTEM SHALL run a `ledger` check that fails when any worktree of the primary checkout has a Ledger failure line from the last 7 days, and reports the count and the latest reason code. *Enforced by:* Wardens test of the doctor check.

### Ring 0 protection of the Ledger path

- WHEN an agent reads, edits, writes or deletes a path inside `~/.local/state/panopticon/ledger/`, or runs a shell command whose text or resolved path words name that directory, THE SYSTEM SHALL deny via `protected-paths` with the message `Blocked by Warden protected-paths: the Ledger is not readable or writable by agents. Label the issue needs:human.` *Enforced by:* Wardens test (ring 0). Interpreters, scripts and variable indirection: **not yet enforced** (Plan, "Trust and integrity").
- WHEN `panopticon.charter.yaml` is validated, THE SYSTEM SHALL reject a `paths.external.read` or `paths.external.write` glob that matches a path inside `~/.local/state/panopticon/ledger/`. *Enforced by:* `charter-validate`, Wardens test.

### Report

- WHEN a human runs `wardens ledger report --since <YYYY-MM-DD>`, THE SYSTEM SHALL print the report in Plan ("Report") as Markdown, and as JSON when `--json` is given. *Enforced by:* Wardens test against recorded `gh` fixtures.
- WHEN `wardens ledger report --backfill` runs, THE SYSTEM SHALL compute the GitHub-based metrics for all PRs merged to `main` since 2026-11-03, and SHALL mark each Ledger-based metric as unavailable for the dates before the first Ledger record. *Enforced by:* Wardens test.
- THE SYSTEM SHALL call `gh` with an argv array and `shell: false`, never through a shell. *Enforced by:* Wardens test on the injected `gh` runner (asserts argv arrays); `spawnSync` options by code review.
- THE SYSTEM SHALL treat PR titles, PR bodies, commit messages and comments as untrusted data (C-20): it SHALL only count them or match them against the fixed patterns in Plan, and SHALL NOT print any part of them. *Enforced by:* Wardens test with a fixture whose title, body, commit message and comment carry a sentinel string and a Markdown injection; the sentinel must not appear in the report.
- THE SYSTEM SHALL print one line per phase-1 criterion with the result `pass`, `fail` or `incomplete`, per Plan ("Phase-1 criteria"). *Enforced by:* Wardens test.
- IF a `gh` call fails, times out or returns JSON that does not parse, THEN THE SYSTEM SHALL print a C-30-style error naming the call and exit 2, and SHALL NOT print a partial report. *Enforced by:* Wardens test.
- THE SYSTEM SHALL exit 0 when the report is printed, whatever the criterion results, and SHALL NOT exit 1. *Enforced by:* Wardens test.

### Tests

- THE SYSTEM SHALL contain Vitest tests for event writing, the no-content rule, write-failure behaviour, concurrent appends, partial lines, rotation, the ring-0 Ledger guard and each report metric against recorded `gh` JSON fixtures. *Enforced by:* `wardens-test`.

## Plan

### Approach

1. A new module `wardens/src/ledger/` holds the record schema, the writer, the reader and the report. The writer is a pure function of the finished verdict, the normalized event, the raw payload's `tool_name` and a few environment facts.
2. `commit()` in `wardens/src/engine.ts` calls the Ledger writer after the per-worktree append, inside its own `try`/`catch`. The record describes the verdict that the tool is actually sent, including an `engine` deny caused by a failed per-worktree append.
3. `definitionOfDone` and `stopEngineFailure` in `wardens/src/dod.ts` return an explicit Stop outcome next to the verdict, so the Ledger does not parse C-30 messages.
4. A built-in ring-0 guard, like the launcher-anchor guard in `wardens/src/guards.ts`, denies agent access to the Ledger directory.
5. `wardens doctor` gains a `ledger` check.
6. `wardens ledger report` reads the Ledger files and calls `gh`.

### Ledger location and enablement

- Directory: `<home>/.local/state/panopticon/ledger/<project>/`. `<home>` is `trustedHome(env)` (`wardens/src/home.ts`). `XDG_STATE_HOME` is ignored, so the ring-0 guard protects one fixed path.
- `<project>` is The Charter's `project` (`lunarhunt` today), read from the trusted primary. It must match `^[a-z0-9][a-z0-9-]{0,63}$`. When The Charter failed to load, or the value does not match, `<project>` is `_unknown`. The report reads `_unknown` as well and counts its records (open question 1).
- Files: `events.jsonl` (current) and `events-<YYYYMMDDTHHMMSSZ>-<pid>.jsonl` (rotated).
- Enablement: the hook writes only when `ledger.sink` contains `jsonl`. Today the value is `[postgres, otlp]`, so nothing is written until Krzysztof changes The Charter (Task 8). The schema already accepts any non-empty string in `sink`; no schema change is needed.
- `ledger.capture_content` is read only for the doctor warning. v0 never writes content.

Permissions, checked by the writer before each open:

- `panopticon`, `ledger` and `<project>` under `~/.local/state/` are created with mode `0700` when missing.
- Each of those three components must be a directory, not a symlink (`lstat`), and owned by the current UID.
- The file is opened with `O_APPEND | O_CREAT | O_NOFOLLOW | O_WRONLY` and mode `0600`. A symlink at the file path fails the open (`ELOOP`); that is a write failure, not a follow.

The symlink rules stop a hook, which runs outside ring 0, from appending agent-influenced text to a file the agent chose.

### Event record

One JSON object per line, written with `JSON.stringify`. A zod `strictObject` validates it before the write. Every key is always present; "nullable" means the value may be `null`, never that the key is missing.

| Key | Type | Nullable | Source |
| --- | --- | --- | --- |
| `v` | `1` | no | constant schema version |
| `record` | `"run_start"` \| `"event"` \| `"run_end"` | no | from the hook event (Acceptance criteria, Event writing) |
| `ts` | string, ISO 8601 UTC with milliseconds | no | `deps.now()` when the verdict is final, same instant as the per-worktree line |
| `project` | string | no | see "Ledger location" |
| `session_id` | string | yes | normalized `session_id`; on a failure path before normalization, raw `session_id`, else raw `conversation_id`, when it is a string |
| `run_id` | string, 32 lowercase hex | yes | first 16 bytes of SHA-256 of `<tool>:<session_id>`; `null` when `tool` or `session_id` is `null` |
| `tool` | `"claude"` \| `"cursor"` | yes | `--tool` when it is a known tool, else `null` |
| `role` | Charter role name | yes | `PANOPTICON_ROLE` when it equals one of `overseer`, `spec-writer`, `implementer`, `reviewer`, `sentinel`, `debugger`; else `null` |
| `model` | string | yes | normalized `model` (payload string only) |
| `agent_type` | string | yes | normalized `agent` (Claude `agent_type`) |
| `event` | string | yes | `--event` when it is a mapped hook event name, `"other"` for any other value, `null` when absent |
| `tool_name` | string | yes | raw payload `tool_name` when it is a string; `null` for events without one |
| `action` | normalized action | yes | normalized `action`, `null` before normalization |
| `decision` | `allow` \| `deny` \| `ask` \| `rewrite` | no | finished verdict `decision` |
| `rendered` | `allow` \| `deny` \| `ask` \| `rewrite` | no | finished verdict `rendered` |
| `warden_rule_id` | string | yes | finished verdict `rule`; `null` when it is `none` |
| `outcome` | Stop outcome | yes | `run_end` only; `null` on other records |
| `interactive` | boolean | no | normalized `interactive`, `false` before normalization |
| `worktree` | string | yes | basename of the git toplevel; `null` without a toplevel |
| `primary` | boolean | no | `true` when the toplevel is the trusted primary checkout |
| `branch` | string | yes | see "Derived fields" |
| `issue` | integer ≥ 1 | yes | see "Derived fields" |
| `duration_ms` | integer ≥ 0 | no | same value as the per-worktree line: verdict time minus start time, before the Ledger write |

String hygiene. Every string except `ts` and `run_id` is kept only when it matches `^[A-Za-z0-9._:/@-]{1,128}$` (`session_id`, `model`, `agent_type`, `tool_name`, `branch`, `worktree`). A value that fails is written as `null`, and `tool_name` is written as `"other"`. This keeps the line bounded and stops a hostile value from carrying text into the file.

Unknown fields per tool today:

| Key | Claude Code | Cursor (frozen, ADR-0017) |
| --- | --- | --- |
| `role` | `null` unless the launch sets `PANOPTICON_ROLE`; nothing sets it today; subagents inherit the parent's value | `null` |
| `model` | only when the payload has a string `model`; Task 4 records which Claude events carry it | present on recorded payloads |
| `agent_type` | set for subagent tool calls only | always `null` |
| `tool_name` | set on `PreToolUse` and `PostToolUse`; `null` on `SessionStart` and `Stop` | set on `preToolUse`; `null` on `beforeShellExecution`, `beforeReadFile`, `beforeMCPExecution`, `afterFileEdit`, `sessionStart`, `stop` |
| `session_id` | always on mapped events | `session_id`, else `conversation_id` |
| `issue` | `null` in subagent worktrees whose branch is still `worktree-agent-<hash>` and that have no task file | same rule |

The report resolves a session's model and role from its `run_start` record when tool records leave them `null`.

### Derived fields and why they are not content

- `worktree` is the last path segment of `git rev-parse --show-toplevel`, for example `98-ledger-v0-spec` or `agent-1a2b3c`. The absolute path, which holds the home directory and user name, is never written.
- `branch` is `git symbolic-ref --quiet --short HEAD` in the toplevel, run with the engine's hardened git options and a 1 second timeout. A detached head, a timeout or an error gives `null`.
- `issue` is the `issue` of a valid, integrity-checked `.panopticon/task.json` (the `TaskState` the hook already loaded); else the number in a branch matching `^[a-z]+/([1-9][0-9]*)-`; else `null`.

These are names, not content. Branch and issue numbers are public on GitHub once pushed. The worktree name is the issue slug or a random hash. None of them carries a prompt, a file body, a command or a path argument. They are still agent-chosen strings, so the hygiene rule above applies.

### Stop outcome

| Outcome | When |
| --- | --- |
| `dod_green` | `definition-of-done` allowed because `pnpm check` ran green, or the fingerprint equals the last green one |
| `dod_red` | `definition-of-done` denied: red or timed out, below the limit |
| `loop_limit` | the third red Stop in a session: allowed with the `needs:human` line (`RED_LIMIT`) |
| `not_run` | the check did not run: nothing to deliver, or Cursor `status` is not `completed` |
| `engine` | a rule threw or the engine failed on a Stop, including the unresolved-toplevel allow |

A denied Stop does not end the session. A session can therefore have several `run_end` records (for example `dod_red`, then `dod_green`). Its final outcome is the outcome of its last `run_end` by `ts`.

`usage_limit` is reserved for #99. v0 does not write it. #99's spec defines when it is written.

### Write path and failure

Order inside `commit()`:

1. Finish the verdict, as today.
2. Append the per-worktree line, as today. If that throws, the verdict becomes `engine` deny, as today.
3. If `ledger.sink` contains `jsonl`, build and append the Ledger record of the verdict from step 1 or 2, inside `try`/`catch`.
4. Return the verdict from step 1 or 2. Step 3 cannot change it.

The no-toplevel path (`fail` with `toplevel: null`, `allowUnresolvedStop`) also writes a Ledger record, with `worktree: null`, `branch: null` and `issue: null`, when The Charter loaded. Without a Charter there is no `sink` value; then nothing is written, and the per-worktree or fallback log stays the only record.

Write budget. The writer does at most: three `lstat`, up to three `mkdir`, one `open`, one `fstat`, one 1-byte `pread`, one `write`, one `close`, and at most one `rename` for rotation. No lock, retry, `fsync`, child process or network call. A hung local filesystem would already hang the per-worktree append, so the Ledger adds no new kind of hang. Hook timeouts (10 s, and 900 s for Stop) are unchanged.

Failure line, `<toplevel>/.panopticon/ledger-failures.jsonl`:

```json
{"ts":"2026-11-20T08:00:00.000Z","project":"lunarhunt","reason":"open"}
```

`reason` is one of `home_unresolved`, `not_directory`, `symlink`, `not_owned`, `mkdir`, `open`, `write`, `too_long`, `schema`, `rotate`. No error text, path or errno string is written. Without a toplevel the failure line is skipped. The line is best effort; an error there is ignored.

### Concurrent appends, partial lines and rotation

Several sessions in several worktrees append to the same file.

- Each record is one `write` of the whole line on an `O_APPEND` descriptor. On local APFS and ext4, such a write moves the offset and writes the bytes as one step, so whole lines from different processes do not interleave. POSIX does not promise this for regular files. Network filesystems are not supported. The doctor check warns when the directory is not on a local filesystem, where the platform can tell.
- Line cap: 4096 bytes with the newline. With the string hygiene rule a record stays well below that. A record over the cap is not written and fails with `too_long`.
- Partial line from an earlier crash or a full disk: before writing, the writer reads the last byte of the file (`fstat` plus a 1-byte `pread`). When the file is non-empty and that byte is not `\n`, it prefixes its line with `\n`. A race can add an empty line; the reader ignores empty lines.
- A short `write` (fewer bytes than the line) is a `write` failure. The writer does not try to complete it.
- Reader: splits on `\n`, ignores empty lines, skips a line that does not parse as JSON or does not match the schema, and counts it as `malformed`. A last line without `\n` is counted as `partial` and skipped. The report header shows both counts.
- Rotation: when `fstat` shows `events.jsonl` at or above 64 MiB, the writer renames it to `events-<UTC time>-<pid>.jsonl` and opens a new `events.jsonl`. A writer that still holds the old descriptor finishes into the renamed file; no line is lost. Two writers that rotate at once produce one extra small rotated file; this is accepted. A failed rename is `rotate` and the line is not written.
- Retention: v0 deletes nothing (open question 2). At an estimated 300 bytes per record and a few thousand hook calls per day, 64 MiB lasts weeks.

### Trust and integrity

The Ledger file lives in Krzysztof's home directory. Hooks and agents run under the same UID. Ring 0 is a guard rail, not a sandbox. v0 has no tamper protection; it does not claim any.

What an agent could do if it reaches the file by a path ring 0 does not see (an interpreter such as `node -e` or `python -c`, a script it wrote, variable indirection, a file descriptor trick):

- **Forge** records: add a `run_start` for its session, add `run_end` with `dod_green`, add or remove `event` records, change `tool`, `role` or `model`.
- **Delete** lines, for example its own deny records.
- **Truncate** or remove `events.jsonl` and the rotated files.
- **Write** into `_unknown` or another project's directory.

It can also influence some fields through normal work, without touching the file: the branch name (`git branch -m` is not denied), its own `task.json` (subject to the integrity hash), and `PANOPTICON_ROLE` of a nested `claude -p` it starts.

Metrics that such tampering would change:

| Metric | Effect |
| --- | --- |
| Warden blocks per task | lowered by deleted deny records; attributed elsewhere by a renamed branch |
| Sessions with tool events but no `run_start` | hidden by a forged `run_start` |
| Records with `warden_rule_id: engine` | hidden by deletion |
| Run outcomes, `loop_limit` counts | forged or hidden |
| Runs with `tool != claude` (ADR-0017) | hidden by an edited `tool` |
| Merged agent PRs without Ledger records | hidden by forged records on that branch |
| Usage-limit stops per day (once #99 writes them) | forged or hidden |
| "Ledger dashboard live" criterion | made `incomplete` by truncation |

Metrics computed from GitHub alone, which the Ledger file cannot change:

- merged agent PRs;
- CI first-pass green rate (check runs come from the GitHub Actions app; a user token can create commit statuses but not check runs, and the report reads check runs only);
- merged agent PRs with a required check not green at merge;
- PR commits without an `Agent:` trailer, and commits on `main` without a merged PR;
- review rounds per PR.

These are not tamper-proof either. Agents use Krzysztof's `gh` token (#94, decision 5). An agent chooses its own trailer text (C-27 is self-reported), and it can post a comment that looks like a review-round header. The report says so next to those metrics. It never says "verified".

Detection, not prevention:

- The per-worktree `.panopticon/wardens.log.jsonl` is a second copy while the worktree exists. v0 does not cross-check it (follow-up).
- The doctor `ledger` check fails on wrong owner, wrong mode or a symlink, and warns on `malformed` or `partial` lines.

The control that would make the file unreachable for agent shell commands is the OS sandbox from #70: a `denyRead` and `denyWrite` entry for `~/.local/state/panopticon/ledger/`, next to the planned `~/.config/panopticon/` entry. Hooks must still be able to write; #70 confirms that hooks run outside the sandbox. That entry is generated from The Charter by `wardens sync`; the Charter change and the sync are Krzysztof's (Task 8).

### Ring-0 Ledger guard

A built-in deny in `wardens/src/guards.ts`, beside the launcher-anchor guard. It is not a Charter key, because the path is fixed by code, as the anchor path is.

- Pattern on paths and shell words: `/\.local\/+state\/+panopticon\/+ledger(\/|$)/i`, plus `/panopticon\/+ledger/i` on raw shell text.
- It applies to `read`, `edit`, `write` and `delete` events (the anchor guard covers mutations only), and to every `shell` event.
- For shell commands it checks the raw text, every argv word, and every resolved path word, using the existing `cd` tracking (`trackedSteps`), so `cd ~/.local/state/panopticon && cat ledger/lunarhunt/events.jsonl` is denied.
- It runs before `paths.external`, so an external allowlist entry cannot open the path. `charter-validate` also rejects such an entry.
- It does not cover `~/.local/state/panopticon/sessions/` (#99), which OVERSEER is meant to read.
- Rule id `protected-paths`, decision `deny`, message as in the acceptance criteria.

`wardens ledger report` is not blocked by this guard: its command text names no Ledger path. Whether agents may run it is open question 4.

### `wardens doctor` check `ledger`

Runs outside `--ci` only. Results:

| Condition | Status |
| --- | --- |
| `ledger.sink` lacks `jsonl` | `warn`: Ledger disabled |
| `ledger.capture_content: true` | `warn`: v0 captures no content |
| `HOME` unresolved | `fail` |
| a directory component is a symlink, not owned by the UID, or not mode `0700`; the file is a symlink or not `0600` | `fail` |
| directory not writable (`access` `W_OK`) | `fail` |
| a `ledger-failures.jsonl` line from the last 7 days in the primary checkout or any linked worktree | `fail`, with the count and the latest `reason` |
| `malformed` or `partial` lines in `events.jsonl` | `warn`, with counts |
| `events.jsonl` above 48 MiB (75% of the cap) | `warn` |
| directory not on a local filesystem, where detectable | `warn` |
| otherwise | `ok` |

The check never writes a probe record into the Ledger. Failure lines in a removed worktree are lost with it; this is accepted, because Krzysztof runs `wardens doctor` at every rollout (ADR-0016 D7).

### Report

Command: `wardens ledger report (--since <YYYY-MM-DD> | --backfill) [--until <YYYY-MM-DD>] [--json] [--repo <owner/repo>]`.

- Dates are UTC days. `--since` is inclusive from 00:00. `--until` is inclusive to 23:59:59.999 and defaults to now. `--backfill` sets `--since 2026-11-03`.
- The repository comes from `--repo`, else from the issue-repository sidecar written by `wardens sync` (`readRepo`), else the command fails.
- Ledger input: every `events*.jsonl` file under `ledger/<project>/` and `ledger/_unknown/`. The report opens them in its own process; the ring-0 guard judges an agent's tool calls, not the files a Wardens process opens.
- A PR is in the window when its `merged_at` is in the window. A Ledger record is in the window when its `ts` is.

#### `gh` calls

All calls go through one injected runner: `spawnSync("gh", argv, { shell: false, timeout: 60_000 })`. Only these argv shapes are used (`{repo}` and numbers are filled in as separate words or inside one URL word):

1. `["api", "--paginate", "repos/{repo}/pulls?state=closed&base=main&per_page=100"]`, keeping PRs with `merged_at` in the window.
2. `["api", "--paginate", "repos/{repo}/pulls/{n}/commits?per_page=100"]`.
3. `["api", "--paginate", "repos/{repo}/actions/runs?event=pull_request&branch={head_ref}&per_page=100"]`. `{head_ref}` is URL-encoded and must match the branch hygiene pattern; otherwise the PR's first SHA is `unknown`.
4. `["api", "--paginate", "repos/{repo}/commits/{sha}/check-runs?per_page=100"]`.
5. `["api", "--paginate", "repos/{repo}/issues/{n}/comments?per_page=100"]`.
6. `["api", "--paginate", "repos/{repo}/commits?sha=main&since={since}T00:00:00Z&per_page=100"]`.

Each response is parsed with zod. Only the fields the metrics need are kept; titles and bodies are dropped at parse time. `--paginate` output that is several JSON arrays is concatenated.

#### Fixed patterns

- Agent trailer: a commit message line matching `^Agent: (claude|cursor) \(.+\)$`, the same pattern as `agent-trailer` (`wardens/src/trailer.ts`). Only the tool group is used. The model text is never printed.
- Review-round header (github-writing skill, ADR-0016 D9): the first line of a PR comment matching `^\*\*(Reviewer|Sentinel) round ([1-9][0-9]?): [0-9]+ blocking, [0-9]+ non-blocking\*\* at [0-9a-f]{7,40}`.
- Required checks: check runs named `check`, `contract`, `charter-drift`, `wardens-test` whose `app.slug` is `github-actions`. Commit statuses are ignored.

#### Metrics

Each metric is defined by inputs, filter, formula and edge cases.

**M1. Merged agent PRs.**
- Inputs: calls 1 and 2.
- Filter: PRs merged into `main` in the window, with at least one PR commit (call 2) that has an agent trailer.
- Formula: the count. The JSON lists PR numbers and the trailer tools seen.
- Edge cases: the commits endpoint returns at most 250 commits; a PR at that limit is marked `commits_truncated`. Renovate PRs have no trailer and are not agent PRs. A human commit with a trailer makes its PR an agent PR (self-reported, see "Trust and integrity").

**M2. CI first-pass green rate.**
- Inputs: M1 PRs, calls 3 and 4.
- First head SHA: the `head_sha` of the earliest `pull_request` workflow run (by `created_at`, then `id`) whose `pull_requests` contains the PR number. If no run lists the PR, the earliest run on its head branch created between the PR's `created_at` and `merged_at`. If there is none, the first SHA is `unknown`.
- Applicable checks: the required check names that have at least one check run on any of the PR's commits (call 4 on the first and final head SHAs). This handles checks that did not exist yet for early PRs.
- First-pass green: for each applicable check, the earliest check run with that name on the first head SHA (by `started_at`, then `id`) has `conclusion: success`. A rerun does not count. `cancelled`, `skipped`, `neutral`, `timed_out`, `failure`, `action_required`, still running, and missing count as not green.
- Formula: green PRs divided by M1 PRs with a known first SHA and at least one applicable check. Printed as a percentage with one decimal, and as `green/denominator`.
- Edge cases: PRs with `unknown` first SHA or no applicable check are excluded from the denominator and listed. A denominator of 0 makes the rate `n/a`.

**M3. Warden bypass candidates.** A candidate is a fact for a human to review, not a finding. Each class is listed with its count and items.
- **B1. Merged with a required check not green.** M1 PRs where an applicable check's latest completed run (any attempt) on the final head SHA (`head.sha` from call 1) is not `success`, or is missing. Source: GitHub.
- **B2. PR commits without a trailer.** Commits of M1 PRs that have one parent and no agent trailer. Merge commits from `main` into the branch are skipped. When Ledger data covers the commit time, each item is marked `in_session: true` if its committer date lies between the first and last record of a session on the PR's head branch. Source: GitHub, Ledger for the mark.
- **B3. Commits on `main` without a merged PR.** Commits from call 6 in the window whose SHA is not the `merge_commit_sha` of any merged PR from call 1. Source: GitHub.
- **B4. Sessions without `run_start`.** Ledger sessions, keyed by `(tool, session_id)`, that have at least one `event` record in the window and no `run_start` record at any time. Records with `session_id: null` are counted on their own line. Source: Ledger.
- **B5. Engine records.** Ledger records with `warden_rule_id: "engine"`, counted by `decision`. This is the AC's "decision: engine" class: in the engine, `engine` is the rule id of a deny or allow, not a decision value. Source: Ledger.
- **B6. Merged agent PRs without Ledger records.** M1 PRs created after the first Ledger record whose head branch has no Ledger record. This is ADR-0010's "sessions without hook events" check at PR level. Source: GitHub and Ledger.

**M4. Warden blocks per task.**
- Input: Ledger `event` records in the window.
- Task key: `issue`, else `branch`, else `worktree`, else `unattributed`.
- Formula per task: the number of records with `rendered: "deny"`, split by `warden_rule_id`. `ask` and `rewrite` are counted in their own columns. Stop records are not blocks; their outcomes appear under M8.
- Edge cases: `engine` denies are counted here and under B5. The report prints the median and maximum over tasks with at least one record.

**M5. Review rounds per PR.**
- Inputs: M1 PRs, call 5.
- Formula per PR and role (`Reviewer`, `Sentinel`): the number of distinct round numbers in matching headers. A PR without headers has `null` for that role, not 0.
- Summary: the count of PRs with headers, the mean and maximum per role, and the PRs above 2 rounds for one role (`review.max_rounds`, ADR-0016 D9).
- Edge cases: all comments are posted with Krzysztof's token, so authorship cannot be checked. A header-shaped comment counts whoever wrote it.

**M6. Usage-limit stops per day.**
- Input: Ledger `run_end` records with `outcome: "usage_limit"`, grouped by UTC day of `ts`.
- Availability: `unavailable` until the window contains at least one Ledger record with `event: "Notification"`, which shows that #99's hook writes to the Ledger. Until then the report does not print 0.

**M7. Runs with `tool != claude` (ADR-0017).**
- Ledger: sessions whose records have `tool: "cursor"` or `tool: null`.
- GitHub: M1 PRs with a `cursor` trailer.
- Formula: two counts with items. Not a phase-1 criterion; a flag for Krzysztof.

**M8. Run outcomes.** Final outcome per session (last `run_end`), counted by outcome, and sessions with no `run_end`. Source: Ledger.

Header lines: window, repository, Ledger coverage start (first record `ts`, or "none"), files read, `malformed` and `partial` line counts, and the count of `_unknown` records.

#### Phase-1 criteria

| Criterion (ADR-0008) | `pass` | `fail` | `incomplete` |
| --- | --- | --- | --- |
| ≥ 20 agent PRs merged | M1 ≥ 20 | M1 < 20 | — |
| CI first-pass green rate ≥ 70% | M2 ≥ 70.0% | M2 < 70.0% | M2 is `n/a` |
| No Warden bypass found | B1–B6 all 0, and Ledger coverage starts on or before `--since` | any class > 0 (lists the classes) | all 0, but Ledger coverage starts after `--since` |
| Ledger dashboard live | the Ledger has at least one record in the window and `malformed` is 0 | — | otherwise |

A `pass` line is a measurement for Krzysztof, not a decision. C-23 still requires a Charter PR approved by Krzysztof to change `autonomy.phase`.

#### Backfill

`--backfill` computes M1, M2, M3 classes B1, B2 (without `in_session` marks) and B3, M5, and the GitHub half of M7 for PRs merged since 2026-11-03. Unavailable for dates before the first Ledger record: B4, B5, B6, M4, M6, the Ledger half of M7, M8 and the `in_session` mark. The report names them in an "Unavailable before <date>" line. The "No Warden bypass found" line is then `incomplete` at best. Review-round headers exist only from the github-writing shape onward; earlier PRs have `null` rounds.

#### Output

- Markdown: a header block, one section per metric, the criteria table last. PR numbers are printed as `#N`. No PR title, branch name or comment text is printed. Branch names and worktree names appear only in M4 task keys and B4 items, after the hygiene filter.
- JSON (`--json`): `{ "v": 1, "window": {…}, "sources": {…}, "metrics": { "m1": …, … }, "criteria": [ { "id", "result", "value", "threshold" } ] }`. The keys are fixed by a zod schema and a golden test.

Write-failure test. The same five hook payloads plus one Stop per outcome run twice: with a working writer and with a writer that throws. Stdout, exit code and the per-worktree line (without `ts` and `duration_ms`) must be byte-equal between the two runs.

## Open questions for Krzysztof

1. **Project name source.** Recommendation: The Charter's `project` from the trusted primary, with `_unknown` when The Charter did not load. Alternative: the primary checkout's directory name, which needs no Charter but changes when the folder is renamed.
2. **Retention.** Recommendation: keep every file in v0 (estimated well under 1 GiB per year); decide deletion when the Postgres import exists. Alternative: a new task that deletes rotated files older than 180 days.
3. **Report in CI.** Recommendation: no in v0. CI has no Ledger file, so only the backfill half would run, and the job would need a token with read access to Actions. A later scheduled workflow can publish the GitHub half.
4. **May agents run `wardens ledger report`?** Recommendation: yes. The output holds only counts, PR numbers and filtered names; OVERSEER needs it for planning. It reads the file inside the bundle process, so it is no new way around the guard beyond the interpreter gap that already exists.
5. **Enablement through `ledger.sink`.** Recommendation: gate writes on `jsonl` in `ledger.sink`, as specified. It keeps policy in The Charter (C-04) and gives a switch-off. Alternative: always write, and leave `sink` for Postgres.
6. **First-pass green on early PRs.** Recommendation: the per-PR "applicable checks" rule in M2, so PRs from before `charter-drift` and `wardens-test` existed are judged on the checks that ran. Alternative: the fixed set of four for every PR, which makes most early PRs fail.
7. **Window for the "≥ 20 agent PRs" line.** Recommendation: the report window, with `--backfill` for the phase entry PR. Alternative: always count from 2026-11-03.
